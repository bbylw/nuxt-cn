---
title: '近乎静态的网站'
description: '为内容型和营销型网站交付几乎为零的 JavaScript，同时保留可交互的孤岛。'
---

默认情况下，Nuxt 会服务端渲染一个页面，然后把整个页面水合。对于一个 95% 都是静态文本和图片的页面，这部分水合 JavaScript 基本上是额外开销：它推迟了可交互时间，还与你的内容争夺带宽和 CPU，从而拖累移动端 PageSpeed 得分这类指标。

Nuxt 已经具备在你不需要时避免这部分成本的各个部件。本配方把它们组合起来：

1. 在构建时**预渲染**你的内容路由。
2. 用 `noScripts` 路由规则在这些路由上**去掉脚本**。
3. 对需要服务端渲染但不需要交互的部件（widget）使用**服务端组件**。
4. 在保留脚本的路由上使用**延迟水合**，让交互开销只在需要时才付出。

## 预渲染并去掉脚本

对于完全没有客户端交互的路由，在 [`routeRules`](/docs/guide/concepts/rendering#hybrid-rendering) 中把 `prerender` 和 `noScripts` 组合起来：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  routeRules: {
    '/blog/**': { prerender: true, noScripts: true },
    '/about': { prerender: true, noScripts: true },
  },
})
```

这些路由会在构建时被渲染成纯 HTML，并且渲染出的页面会省略 Nuxt 入口脚本、import map、payload 脚本和 JS 资源提示。CSS 仍然包含在内。最终得到的页面 JavaScript 成本实际上为零。

:::read-more{to="/docs/guide/going-further/features#noscripts"}
阅读更多关于 `noScripts` 究竟会省略哪些内容，以及应用级别的 `features.noScripts` 选项。
:::

:::important
`noScripts` 页面不会水合。页面上没有任何东西是可交互的：没有 `@click` 处理函数，没有 `<NuxtLink>` 预取（链接仍然可以作为普通的 `<a>` 标签工作），也没有离开该页面的客户端导航。请只在确实需要这样做的路由上使用它。
:::

## 在无脚本路由之间导航

因为 `noScripts` 页面没有客户端路由，所以进出它的一次次导航都是整页加载。这两个方向 Nuxt 都会替你处理：

- 从有脚本的路由导航**到**一个 `noScripts` 路由（用 `navigateTo`、`<NuxtLink>` 或 `router.push`）会触发一次文档加载，因此目标由服务端以无脚本的方式交付，而不是由客户端路由渲染。
- 由于这些路由永远不会在客户端渲染，当覆盖它们的路由规则可以在构建时被解析出来时，它们的页面组件会从客户端 bundle 中剔除。
- 无论是有脚本的页面还是无脚本的页面，都会发出一个声明式的[推测规则（speculation rules）](https://developer.mozilla.org/en-US/docs/Web/API/Speculation_Rules_API)标签，让支持的浏览器在用户点击链接之前就预取并预渲染目标。这不会在页面本身运行任何 JavaScript，并且这些规则被限定在你的页面路由范围内，因此指向某个服务端路由（例如 `/logout`）的链接永远不会被推测性地获取。

启用[实验性视图过渡](/docs/getting-started/transitions#view-transitions-api-experimental)后，这些页面也会加入跨文档视图过渡，于是整页导航会有动画而不是一闪而过：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    viewTransition: true,
  },
})
```

## 用孤岛承载服务端渲染的部件

静态页面中的某些部分仍然适合做成背后有真实逻辑的组件：渲染后的 markdown、带语法高亮的代码、CMS 内容。对这些场景请使用[服务端组件](/docs/guide/concepts/server-components)。它们在服务端渲染，而它们的依赖永远不会进入客户端 bundle：

```bash [Directory Structure]
-| app/
---| components/
-----| HighlightedMarkdown.server.vue
```

```vue [app/pages/blog/[slug\\].vue]
<template>
  <article>
    <h1>{{ post.title }}</h1>
    <HighlightedMarkdown :markdown="post.body" />
  </article>
</template>
```

像这样的静态孤岛（island）在 `noScripts` 路由上工作正常，因为它们的 HTML 在渲染时就已嵌入。

:::warning
孤岛内部完全可交互的部件（标记了 [`nuxt-client`](/docs/guide/concepts/server-components#selective-hydration-with-nuxt-client) 的组件，或可交互的孤岛插槽）在 `noScripts` 路由上**不能**工作。孤岛 teleport 的内容是在水合之前由一小段内联脚本重定位到位的；脚本被禁用时，这段重定位无法运行，也就没有任何东西会水合。如果一个页面哪怕只需要一个可交互的部件，请在该路由上保留脚本，改用延迟水合。
:::

## 其余部分使用延迟水合

对于需要一些交互的路由，保持脚本启用，但用[延迟水合](/docs/directory-structure/app/components#delayed-or-lazy-hydration)来控制组件*何时*水合：

```vue [app/pages/index.vue]
<template>
  <div>
    <HeroSection />
    <!-- 永远不需要变成可交互的静态内容 -->
    <LazyTestimonials hydrate-never />
    <!-- 只在滚动进入视图时水合 -->
    <LazyNewsletterSignup hydrate-on-visible />
    <!-- 在浏览器空闲时水合 -->
    <LazyCookieBanner hydrate-on-idle />
  </div>
</template>
```

`hydrate-never` 在内容型网站上尤其有用：组件的 HTML 是服务端渲染的，但它永远不会被水合，因此它的 JavaScript 永远不会执行（不过 prop 变化仍会触发水合）。

## 组合起来

一个典型的近乎静态的网站最终会是这样的：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  routeRules: {
    // 纯内容：预渲染，零 JS
    '/': { prerender: true, noScripts: true },
    '/blog/**': { prerender: true, noScripts: true },
    // 带一个可交互部件的页面：预渲染，保留脚本
    '/contact': { prerender: true },
  },
})
```

- 内容路由交付纯 HTML 和 CSS，而指向它们的导航是一次被推测性预取的文档加载
- 孤岛（`.server.vue` 组件）在所有地方承担服务端渲染的部件，把沉重的依赖挡在客户端 bundle 之外
- 少数几个需要交互的路由保留脚本，并用 `hydrate-on-visible` / `hydrate-on-idle` / `hydrate-never` 限制浏览器一开始要做多少工作

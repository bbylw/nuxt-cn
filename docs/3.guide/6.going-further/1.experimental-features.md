Nuxt 包含可在配置文件中启用的实验性特性。

在内部，Nuxt 使用 `@nuxt/schema` 来定义这些实验性特性。你可以参考 [API 文档](/docs/guide/going-further/experimental-features) 或[源代码](https://github.com/nuxt/nuxt/blob/main/packages/schema/src/config/experimental.ts) 了解更多信息。

:::note
请注意，这些特性是实验性的，未来可能会被移除或修改。
:::

## alwaysRunFetchOnKeyChange

是否在 key 改变时运行 `useFetch`，即使它被设置为 `immediate: false` 且尚未被触发。

如果 `immediate: true` 或它已经被触发过，`useFetch` 和 `useAsyncData` 在 key 改变时总是会运行。

这个标志默认是禁用的，但你可以启用此特性：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    alwaysRunFetchOnKeyChange: true,
  },
})
```

## appManifest

使用应用 manifest 以在客户端遵循路由规则。

这个标志默认是启用的，但你可以禁用此特性：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    appManifest: false,
  },
})
```

## asyncContext

启用原生 async 上下文，使其在 Nuxt 和 Nitro 中的嵌套组合式函数中可访问。这为在 async 组合式函数内部使用组合式函数打开了可能性，并减少了遇到 `Nuxt instance is unavailable`（Nuxt 实例不可用）错误的机会。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    asyncContext: true,
  },
})
```

## asyncEntry

为 Vue bundle 生成异步入口点，辅助模块联邦支持。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    asyncEntry: true,
  },
})
```

## extractAsyncDataHandlers

从 `useAsyncData` 和 `useLazyAsyncData` 调用中提取处理函数到独立的 chunk 中，以改善代码分割和缓存效率。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    extractAsyncDataHandlers: true,
  },
})
```

此特性将内联的处理函数转换为动态导入的 chunk：

```vue
<!-- 转换前 -->
<script setup>
const { data } = await useAsyncData('user', async () => {
  return await $fetch('/api/user')
})
</script>
```

```vue
<!-- 转换后 -->
<script setup>
const { data } = await useAsyncData('user', () =>
  import('/generated-chunk.js').then(r => r.default()),
)
</script>
```

这种转换的好处是，我们可以拆分出数据获取逻辑——同时仍然允许在需要时加载这些代码。

:::important
此特性仅推荐用于**带有 payload 提取的静态构建**，且数据不需要在运行时重新获取的情况。
:::

## emitRouteChunkError

当加载 vite/webpack chunk 出现错误时，发出 `app:chunkError` 钩子。默认行为是在导航到新路由时，当某个 chunk 加载失败时执行新路由的重新加载。

默认情况下，当导航到新路由时某个 chunk 加载失败，Nuxt 也会执行新路由的重新加载（`automatic` 自动）。

设置为 `automatic-immediate` 会让 Nuxt 在 chunk 加载失败时立即执行当前路由的重新加载（而不是等待导航）。这对于非由导航触发的 chunk 错误很有用，例如当你的 Nuxt 应用未能加载某个[懒加载组件](/docs/directory-structure/app/components#dynamic-imports) 时。这种行为的一个潜在缺点是产生不期望的重新加载，例如当你的应用并不需要导致错误的那个 chunk 时。

你可以将此设为 `false` 来禁用自动处理，或设为 `manual` 来手动处理 chunk 错误。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    emitRouteChunkError: 'automatic', // 或 'automatic-immediate'、'manual' 或 false
  },
})
```

## enforceModuleCompatibility

当某个 Nuxt 模块不兼容时，Nuxt 是否应抛出错误（并加载失败）。

此特性默认是禁用的。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    enforceModuleCompatibility: true,
  },
})
```

## restoreState

在 chunk 错误或手动调用 [`reloadNuxtApp()`](/docs/api/utils/reload-nuxt-app) 后重新加载页面时，允许从 `sessionStorage` 恢复 Nuxt 应用状态。

为了避免水合错误，它只会在 Vue 应用挂载之后应用，这意味着初始加载时可能会出现闪烁。

:::important
在启用此特性前请仔细考虑，因为它可能导致意外行为，并考虑为 [`useState`](/docs/api/composables/use-state) 提供显式 key，因为自动生成的 key 可能在构建之间不匹配。
:::

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    restoreState: true,
  },
})
```

## parseErrorData

:::warning
此选项已被弃用，未来会被移除。它始终被强制开启，对它的设置会被忽略。
:::

是否在渲染服务端错误页面时解析 `error.data`。

它之所以存在，是因为过去错误是以一组单独的查询参数传给错误页面的，这会把 `error.data` 字符串化，因此必须再解析回来。把它设为 `false` 会跳过该解析，让你只得到一个字符串。

现在整个错误会被一次性 JSON 编码，因此 `error.data` 到达时保持原有结构，永远不会被字符串化。

## payloadExtraction

控制预渲染和缓存（ISR/SWR）页面的 payload 数据如何传递。

- `'client'` - payload 在初始服务端渲染时内联在 HTML 中，并为客户端导航提取到 `_payload.json` 文件。
- `true` - payload 提取为单独的 `_payload.json` 文件，用于初始服务端渲染和客户端导航。
- `false` - 完全禁用 payload 提取。payload 始终内联在 HTML 中，不会生成任何 `_payload.json` 文件。

默认值为 `'client'`。当设置了 `ssr: false` 时，它会被强制设为 `false`。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    payloadExtraction: 'client',
  },
})
```

::read-more{to="/docs/getting-started/prerendering#payload-extraction"}
阅读更多关于 payload 提取以及每种模式的后果。
::

## clientNodePlaceholder

在服务端渲染期间，使用注释节点（`<!--placeholder-->`）代替 `<div>` 元素作为仅客户端组件的占位符。

启用后，`.client.vue` 组件和 `createClientOnly()` 包装器会在服务端渲染一个 HTML 注释，而不是一个空的 `<div>`。这修复了一个 Vue 水合问题：当占位 `<div>` 与实际组件的根元素共享相同的标签名时，作用域样式可能不会被应用。

:::warning
启用这意味着传递给 `.client.vue` 组件的属性（`class`、`style` 等）不会出现在 SSR 的 HTML 中。如果你需要带样式的占位符以防止布局偏移，请改用带 `#fallback` 插槽的 `<ClientOnly>`。
:::

此标志默认启用，但你可以禁用它：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    clientNodePlaceholder: false,
  },
})
```

## serverPathFallback

把匹配不到任何页面路由的客户端导航当作完整文档来加载，这样服务端就能用 `public/` 中的文件、一条服务端路由或它自己的 404 页面来响应。启用后，`<NuxtLink to="/brochure.pdf">` 和 `<NuxtLink to="/rss.xml">` 在点击时和整页加载时表现一致。

如果当前文档本来就是为该路径提供的，那么该路径永远不会被重新加载，因此对那些会用 SPA 回退响应未知路径的托管环境来说，仍会渲染客户端的 404 页面。

此标志默认启用，但你可以禁用它：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    serverPathFallback: false,
  },
})
```

启用 `hashMode` 时，该选项没有任何效果。

## early404

对于路径不可能匹配任何页面路由的请求，直接提前返回 404 错误，而不在服务端加载 Vue 应用、它的插件或中间件。

页面路由（包括别名）会在构建时被编译进一个静态路由匹配器，进入的请求会在服务端渲染开始之前与它比对。无法匹配任何页面的请求会完全跳过加载应用，直接进入错误页面。

覆盖该路径的 [`cache` 路由规则](/docs/guide/concepts/rendering#hybrid-rendering) 也会在 GET/HEAD 未命中时把它的 `maxAge` 作为 `Cache-Control` 报出，让 CDN 吸收对未知路径的重复请求。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    early404: true,
  },
})
```

:::warning
这是一个需要主动开启的选项，因为它可能破坏依赖运行时路由的应用：

- 在插件中用 `router.addRoute()` 动态添加的页面。为了尽早暴露这类问题，启用该选项后，[`useRouter`](/docs/api/composables/use-router) 返回的 router 类型上会移除 `addRoute`。
- 把未知路径重定向到已有页面的路由中间件

在开发模式下、启用 `hashMode` 时、存在能匹配所有路径的根级 catch-all 页面（例如 `pages/[...slug].vue`）时，以及自定义的 `app/router.options` 文件可能修改 `routes` 时（若该文件的默认导出是不含 `routes` 键的普通对象，则仍然兼容），该选项会被自动禁用。
:::

[`staticRoutes`](#staticroutes) 会启用该选项。

## staticRoutes

把页面路由视为在应用构建完成后即固定不变，这让 Nuxt 可以跳过那些仅为支持运行时变化的路由表而存在的工作。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    staticRoutes: true,
  },
})
```

启用该选项后：

- 服务端会为每个不同的 `routes` 数组只构建一次路由匹配器，而不是每个请求一次。在一个有几百个页面的应用上，这大约会把一个小页面的服务端耗时减半。
- 除非你自己把它设为 `false`，否则 [`early404`](#early404) 会被启用。
- `router.addRoute()`、`router.removeRoute()` 和 `router.clearRoutes()` 会抛出错误，并且从 [`useRouter`](/docs/api/composables/use-router) 返回的 router 类型上被移除。请改用 [`pages:extend`](/docs/api/advanced/hooks#nuxt-hooks-build-time) 钩子来添加路由，让它们成为构建的一部分。

## templateDiagnostics

针对 Vue 编译器无法检测到的模板错误，在构建时发出警告，因为这些问题依赖于 Nuxt 对你应用的了解：

- [`NUXT_B4025`](/docs/errors/b4025)：`to` 为静态字符串但不匹配任何页面路由的 `<NuxtLink>`
- [`NUXT_B3014`](/docs/errors/b3014)：在服务端组件上使用 `v-on` 或 `v-model`
- [`NUXT_B3015`](/docs/errors/b3015)：把函数或类的实例作为 prop 传给服务端组件，或传入 `<NuxtIsland>` 的 `props`

警告会连同模板位置一起打印在终端里，并在开发模式下显示在每个已打开的页面上，直到问题被修复。

此标志默认启用，但你可以禁用此特性：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    templateDiagnostics: false,
  },
})
```

:::warning
路由检查看不到在运行时用 `router.addRoute()` 添加的路由，也看不到被路由中间件重定向过的路径；当自定义的 `app/router.options` 文件可能修改 `routes` 时，该检查会被跳过。
:::

## ssrErrorBoundary

允许 [`<NuxtErrorBoundary>`](/docs/api/components/nuxt-error-boundary) 捕获在服务端渲染其默认插槽时抛出的错误。随后边界会在服务端渲染它的 `#error` 插槽，并且被捕获的错误会被序列化进 payload，让客户端水合到相同的状态，而不是让错误逃逸到顶层错误页面。

此标志默认启用。禁用后，`<NuxtErrorBoundary>` 只会捕获客户端错误，内容抛出错误的服务端渲染页面仍会显示错误页面。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    ssrErrorBoundary: false,
  },
})
```

## deferPrefetchHints

## strictRouteTypes

拒绝请求到没有任何服务端路由响应的路径。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    strictRouteTypes: true,
  },
})
```

无论该选项设成什么，Nuxt 都会依据你的服务端将要响应的路由来为 `$fetch` 和 `useFetch` 推导类型，因此响应由真正应答它的那个处理器决定。该选项决定的是：一个 Nuxt 无法识别的路径究竟算作错误，还是仅仅被推导为 `unknown`。

- `false`（默认）—— Nuxt 无法识别的路径会被接受并解析为 `unknown`，并且不会拒绝任何方法。Nuxt 看不到请求可能被应答的所有方式：nitro 中间件、[`routeRules`](/docs/guide/concepts/rendering#hybrid-rendering) 代理或一个 catch-all 处理器都可能响应没有任何路由描述过的路径。
- `true` —— 只接受你的服务端构建器所上报的路由，且仅限它们响应的方法。
- `'isomorphic'` —— 与 `true` 相同，另外把你的页面作为返回 `string` 的 `GET` 路由一并纳入，因此 `$fetch('/about')` 会按 Vue 路由所提供的那个路由来推导类型，而不是被拒绝。

启用该选项后，拼写错误和路由并不响应的方法都会成为错误：

```ts
// server/api/todos.post.ts 只响应 POST
await $fetch('/api/todos', { method: 'POST' })
await $fetch('/api/todo', { method: 'POST' })
//           ^ 没有 POST 路由匹配 '/api/todo'
await $fetch('/api/todos')
//           ^ 没有 GET 路由匹配 '/api/todos'
```

有两类请求仍然被接受，因为它们不属于 Nuxt 能描述的范围：绝对 URL（`$fetch('https://example.com')`），以及在运行时拼出来的路径——后者无论该选项是否开启都会解析为 `unknown`。`baseURL` 会先被解析进路径再去匹配，因此经由它发出的请求会按它实际询问的那条路由来检查。显式标注响应类型同样会让这次调用退出检查，因为一旦标注，该请求就不再参与推导：

```ts
const data = await $fetch<{ id: string }>(`/api/${resource}`)
```

:::note
`public/` 目录中的文件并不是你的服务端构建器所上报的路由，因此在启用 `strictRouteTypes` 时请求它们会报错。请带上显式的响应类型去获取它们，或者不开启该选项。
:::

只在你的路由可以被穷举的地方设置它。一个带有 catch-all 页面的应用在 `'isomorphic'` 下会匹配所有路径，这虽然正确，但也意味着该选项约束不了任何东西。

:::read-more{to="/docs/getting-started/data-fetching#typed-routes"}
阅读更多关于类型化路由，以及如何声明一个 Nuxt 看不见的路由。
:::

## watcher

设置一个替代的 watcher，它将被用作 Nuxt 的监视服务。

Nuxt 默认使用 `chokidar-granular`，它会忽略被排除在监视之外的最高级别目录（如 `node_modules` 和 `.git`）。

你可以改为将其设为 `parcel` 来使用 `@parcel/watcher`，这可能会提升大型项目或 Windows 平台上的性能。

你也可以将其设为 `chokidar` 来监视源目录中的所有文件。

设为 `'builder'` 可重用活动构建器自身的文件监视器（例如 Vite 的 `server.watcher`），而不是再启动第二个。这会减少开发模式下活动的文件监视器数量，并且是默认值。如果活动构建器没有实现自身的监视器（目前是 webpack、Rsbuild 和 rspack），Nuxt 会记录警告并回退到它的默认选择。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    watcher: 'chokidar-granular', // 'chokidar'、'parcel' 或 'builder' 也可以
  },
})
```

## sharedPrerenderData

Nuxt 会自动在预渲染的页面之间共享 payload *数据*。当预渲染那些使用 `useAsyncData` 或 `useFetch` 且在不同页面获取相同数据的站点时，这可以带来显著的性能提升。

如果需要，你可以禁用此特性。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    sharedPrerenderData: false,
  },
})
```

:video-accordion{title="观看 Alexander Lichter 关于实验性 sharedPrerenderData 的视频" videoId="1jUupYHVvrU"}

在启用此特性时，特别重要的是确保你数据的任何唯一 key 始终可解析为相同的数据。例如，如果你使用 `useAsyncData` 来获取与特定页面相关的数据，你应该提供一个能唯一匹配该数据的 key。（`useFetch` 应该会为你自动做到这一点。）

```ts
// 这在动态页面（例如 `[slug].vue`）中是不安全的，因为路由 slug 会影响获取的数据，
// 但 Nuxt 无法知道这一点，因为它没有反映在 key 中。
const route = useRoute()
const { data } = await useAsyncData(async (_nuxtApp, { signal }) => {
  return await $fetch(`/api/my-page/${route.params.slug}`, { signal })
})
// 相反，你应该使用一个能唯一标识所获取数据的 key。
const { data } = await useAsyncData(route.params.slug, async (_nuxtApp, { signal }) => {
  return await $fetch(`/api/my-page/${route.params.slug}`, { signal })
})
```

## extraPageMetaExtractionKeys

`definePageMeta()` 宏是收集页面构建时元数据的有用方式。Nuxt 本身提供了一组受支持的 key 列表，用于驱动一些内部特性，如重定向、页面别名和自定义路径。

此选项允许在使用 `scanPageMeta` 时传入额外的 key 来从页面元数据中提取。

```vue
<script lang="ts" setup>
definePageMeta({
  foo: 'bar',
})
</script>
```

```ts
export default defineNuxtConfig({
  experimental: {
    extraPageMetaExtractionKeys: ['foo'],
  },
  hooks: {
    'pages:resolved' (ctx) {
      // ✅ foo 可用
    },
  },
})
```

这允许模块在构建上下文中访问页面元数据中的额外元数据。如果你在模块内使用它，还建议[用你的 key 增强 `NuxtPage` 类型](/docs/directory-structure/app/pages#typing-custom-metadata)。

## extractSerializablePageMeta

默认启用。

默认情况下，Nuxt 在构建时只读取一份固定的 `definePageMeta()` key 列表（再加上 `extraPageMetaExtractionKeys` 中的内容）；其余内容都在运行时从每个页面单独生成的模块中解析。启用该选项后，Nuxt 会把每个可 JSON 序列化的属性直接写入生成的路由记录中。

当一个页面的 `definePageMeta()` 的每个属性都能静态解析时，该路由就完全不再导入这个页面的 meta 模块，从而在开发模式的模块图中为每个页面少掉一个模块。

```vue
<script lang="ts" setup>
definePageMeta({
  layout: { name: 'admin', props: { collapsed: true } },
  title: 'Dashboard',
})
</script>
```

值无法被序列化的属性（函数、变量引用、展开、计算键）不受影响，仍会在运行时解析。

当 [`scanPageMeta`](#scanpagemeta) 为 `false` 时，该选项没有效果，因为此时路由记录不会覆盖 meta 模块。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    extractSerializablePageMeta: false,
  },
})
```

## navigateToEarlyReturn

当导航成功时，把 `<script setup>` 中顶层的 `await navigateTo()` 调用转换为从编译后的 `setup()` 函数提前返回。

没有这个标志时，`await navigateTo()` 之后的代码仍会继续运行，这可能让后面的代码（包括后续的 `navigateTo` 调用）覆盖掉这次重定向，或试图用缺失的数据渲染页面。启用这个标志后，一次成功的导航会停止你其余 setup 代码的执行，并且在导航进行期间组件只渲染一个占位注释。

此标志默认启用，但你可以禁用它：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    navigateToEarlyReturn: false,
  },
})
```

```vue [pages/example.vue]
<script setup lang="ts">
const { data } = await useFetch('/api/data')

if (!data.value) {
  await navigateTo('/fallback')
}

// 启用该标志后，只有在导航没有发生时这段代码才会运行
const processed = data.value!.map(item => item.name)
</script>
```

这个转换只适用于 `<script setup>` 中结果未被使用的顶层 `await navigateTo()` 语句。带有 `open` 选项的调用（或无法静态分析的选项）不会被转换，因为它们不应该阻止当前页面渲染。

只有在导航成功时（也就是 `navigateTo` 解析为 `undefined` 时）才会提前返回。如果导航被中止或失败（例如被导航守卫拦截，或导航到当前路由），其余的 setup 代码会继续运行。在一次成功的导航之后，`navigateTo` 调用之后的任何内容都不会执行：其中包括 `defineExpose` 以及 `<script setup>` 中更靠后的任何生命周期钩子注册。

:::read-more{icon="i-simple-icons-github" to="https://github.com/nuxt/nuxt/issues/23698" target="_blank"}
完整说明见 GitHub issue。
:::

## normalizeComponentNames

Nuxt 会更新自动生成的 Vue 组件名称，使其匹配你用于自动导入该组件的完整组件名。

如果遇到问题，你可以禁用此特性。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    normalizeComponentNames: false,
  },
})
```

默认情况下，如果你没有手动设置，Vue 会分配一个匹配组件文件名的组件名。

```bash [Directory structure]
├─ components/
├─── SomeFolder/
├───── MyComponent.vue
```

在这种情况下，就 Vue 而言，组件名将是 `MyComponent`。如果你想对它使用 `<KeepAlive>`，或在 Vue DevTools 中识别它，你需要使用这个组件。

但为了自动导入它，你需要使用 `SomeFolderMyComponent`。

通过设置 `experimental.normalizeComponentNames`，这两个值会匹配，Vue 会生成一个匹配 Nuxt 组件命名模式的组件名。

## normalizePageNames

确保页面组件名匹配它们的路由名。这会在页面组件上设置 `__name` 属性，以便 Vue 的 `<KeepAlive>` 能按名称正确识别它们。

默认情况下，Vue 基于文件名分配组件名。例如，`pages/foo/index.vue` 和 `pages/bar/index.vue` 都会有组件名 `index`。这使得基于名称的 `<KeepAlive>` 过滤不可靠，因为多个页面共享同一名称。

启用 `normalizePageNames` 后，页面组件会以它们的路由命名（例如 `foo` 和 `bar`），这样你就可以在 `<KeepAlive>` 中使用 `include`/`exclude`，而无需给每个页面手动添加 `defineOptions({ name: '...' })`。

此标志默认启用，但你可以禁用此特性：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    normalizePageNames: false,
  },
})
```

```vue [app.vue]
<template>
  <NuxtPage :keepalive="{ include: ['foo'] }" />
</template>
```

## spaLoadingTemplateLocation

在渲染一个仅客户端页面（使用 `ssr: false`）时，Nuxt 可以可选地渲染一个加载屏幕，内容来自 [`spa-loading-template.html`](/docs/directory-structure/app/spa-loading-template)。

默认值（`'body'`）下，模板会与 Nuxt 应用根一起渲染，并被包裹在一个 loader 元素中：

```html
<div id="__nuxt"></div>
<div id="__nuxt-loader">
  <!-- spa 加载模板 -->
</div>
```

一旦首个页面准备好渲染（包括页面中的异步 setup），这个 loader 元素就会被移除，从而避免加载屏幕与页面之间出现白屏闪烁。你可以用 [`app.spaLoaderTag`](/docs/api/nuxt-config#spaloadertag) 和 [`app.spaLoaderAttrs`](/docs/api/nuxt-config#spaloaderattrs) 来自定义它。Nuxt 是通过 `id` 来找到并移除该元素的，所以如果你修改了 `spaLoaderAttrs`，请保留其中的 `id`。

或者，你可以把它设为 `'within'`，将模板渲染在 Nuxt 应用根内部：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    spaLoadingTemplateLocation: 'within',
  },
})
```

这样渲染出来的结果是：

```html
<div id="__nuxt">
  <!-- spa 加载模板 -->
</div>
```

在这种情况下，模板会在 Vue 挂载应用的那一刻被移除，因此在首个页面准备好渲染之前，屏幕可能是空白的。

## decorators

此选项在整个 Nuxt/Nitro 应用中启用装饰器语法。

当使用 Vite 构建器（默认）时，装饰器通过 [Babel](https://babeljs.io/) 使用 [`@babel/plugin-proposal-decorators`](https://babeljs.io/docs/babel-plugin-proposal-decorators) 降级。当使用 webpack 或 rspack 构建器时，装饰器通过 [esbuild](https://github.com/evanw/esbuild/releases/tag/v0.21.3) 降级。当使用 Rsbuild 构建器时，装饰器通过 [SWC](https://rsbuild.rs/config/source/decorators) 降级。

长期以来，TypeScript 通过 `compilerOptions.experimentalDecorators` 支持装饰器。这个实现早于 TC39 标准化过程。现在，装饰器是一个 [Stage 3 提案](https://github.com/tc39/proposal-decorators)，并且无需特殊配置即在 TS 5.0+ 中支持（参见 https://github.com/microsoft/TypeScript/pull/52582 和 https://devblogs.microsoft.com/typescript/announcing-typescript-5-0-beta/#decorators）。

启用 `experimental.decorators` 启用的是对 TC39 提案的支持，**而不是**对 TypeScript 之前 `compilerOptions.experimentalDecorators` 实现的支持。

:::warning
请注意，在最终落地到 JS 标准之前可能会有所变化。
:::

### 用法

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    decorators: true,
  },
})
```

当使用 Vite 构建器或 Nitro 服务端构建时，你需要将额外的 Babel 包安装为开发依赖：

:::code-group
```bash [npm]
npm install -D @babel/plugin-proposal-decorators @babel/plugin-syntax-jsx
```
```bash [pnpm]
pnpm add -D @babel/plugin-proposal-decorators @babel/plugin-syntax-jsx
```
```bash [yarn]
yarn add -D @babel/plugin-proposal-decorators @babel/plugin-syntax-jsx
```
:::

:::tip
如果这些包尚未存在，Nuxt 会提示你自动安装它们。
:::

```ts [app/app.vue]
function something (_method: () => unknown) {
  return () => 'decorated'
}

class SomeClass {
  @something
  public someMethod () {
    return 'initial'
  }
}

const value = new SomeClass().someMethod()
// 这会返回 'decorated'
```

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    defaults: {
      nuxtLink: {
        componentName: 'NuxtLink',
        prefetch: true,
        prefetchOn: {
          visibility: true,
        },
      },
      useAsyncData: {
        deep: true,

        resetOnClear: true,
      },

        noopener: true,
      },

  },

```

`useState.resetOnClear` 选项控制 [`clearNuxtState`](/docs/api/utils/clear-nuxt-state) 是否将状态重置为其初始值（由 [`useState`](/docs/api/composables/use-state) 的 `init` 函数提供），而不是设为 `undefined`。这默认为 `true`。

`navigateTo.noopener` 选项控制当 [`navigateTo`](/docs/api/utils/navigate-to) 带 `open` 选项被调用、且没有设置 `open.windowFeatures.noopener` 时，它是否向 `window.open` 传入 `noopener`。这默认为 `true`。

## purgeCachedData

是否在路由导航时清理 Nuxt 的静态和 asyncData 缓存。

这个标志默认是启用的，但你可以禁用此特性：

## prefetchPreloadTags

当 `<NuxtLink>` 被预取，且目标路由启用了 [payload 提取](#payloadextraction)（预渲染和缓存路由的默认行为）时，将目标路由通过 [`useHead`](/docs/api/composables/use-head)（或通过像 [`@nuxt/image`](https://image.nuxt.com) 的 `<NuxtImg preload>` 这样的模块）设置的任何 `<link rel="preload">` 提示转发到当前文档。

被转发的链接会从 `rel="preload"` 降级为 `rel="prefetch"`，只有 `as="image"` 的提示例外，它们保留 `rel="preload"`，但会去掉任何 `fetchpriority`。

只转发用户自定义的 head 标签；构建时的 JS/CSS chunk 预加载已经由预取管道单独处理。

这个标志默认是关闭的，因为结合 `prefetchOn: 'visibility'`（`<NuxtLink>` 的默认行为），它可能会一次性触发大量跨路由预取。当你确信目标预加载值得为你用户通常会遇到的链接转发时，再启用它。

对于用户从未访问的路由上每个被转发的图片提示，Chromium 和 Safari 都会记录一条 `was preloaded using link preload but not used within a few seconds` 警告。被转发的图片请求也不携带 `Purpose: prefetch` 头部，因此它们在图片 CDN 的配额、速率限制和统计中会被算作普通流量。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    prefetchPreloadTags: true,
  },
})
```

参见 issue #34953 了解动机。

## pendingWhenIdle

`pendingWhenIdle` 控制 `useAsyncData` 和 `useFetch` 返回的 `pending` ref。

当 `pendingWhenIdle` 为 `false`（默认）时，在进行中的请求期间 `pending` 为 `true`，并与 `status === 'pending'` 匹配。当 `status` 为 `idle` 时，`pending` 保持为 `false`。你可以在 `{ immediate: false }`，或在服务端渲染期间的 `{ server: false }` 中看到这一点。

将 `pendingWhenIdle` 设为 `true`，这样当 `status` 为 `idle` 且没有可用缓存数据时，`pending` 也为 `true`。当你的加载 UI 需要区分 `idle` 和进行中的请求时，使用 `status`。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    pendingWhenIdle: true,
  },
})
```

## entryImportMap

默认情况下，Nuxt 使用 import map 解析 bundle 的入口 chunk，从而提升 chunk 稳定性。

## ssrStreaming

启用 SSR 流式传输，以显著改善 Time to First Byte（TTFB）。启用后，服务器会立即发送 HTML 外壳（包括 `<head>`、样式、预加载提示和入口脚本），然后使用 Vue 的 `renderToWebStream` 渐进式地流式传输渲染后的 body 内容。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    ssrStreaming: true,
  },
})
```

对于机器人和爬虫用户代理（如 Googlebot、Bingbot 等），流式传输会自动禁用，以确保搜索引擎收到完全渲染的 HTML 以符合 SEO 安全。默认的模式只匹配用于索引的爬虫；Lighthouse 和其它审计工具被有意排除在外，因此合成测量反映的正是真实用户得到的同一份流式响应。

你可以用 `botRegex` 自定义哪些用户代理不参与流式传输。`user-agent` 头部匹配该模式的请求**不会**被流式传输：它会收到完全渲染、经过缓冲的 HTML。不匹配的请求则会被流式传输。设置 `botRegex` 会**替换**默认模式而不是在其基础上追加，因此请把你不希望参与流式传输的每个爬虫都列出来：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    ssrStreaming: {
      botRegex: /googlebot|bingbot|my-internal-crawler/i,
    },
  },
})
```

你也可以使用 `routeRules` 按路由控制流式传输：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    ssrStreaming: true,
  },
  routeRules: {
    '/no-stream/**': { streaming: false },
  },
})
```

:::warning
**自动回退到非流式渲染。** 流式传输在外壳刷新时立即提交响应状态码和头部，这与需要在渲染后修改响应的特性不兼容。匹配以下任何情况的请求不会被流式传输；它们使用缓冲渲染器，或短路为重定向或错误响应：

- `routeRules` 为该路由设置了 `noScripts`、`cache`、`isr`、`swr`、`redirect`，或 `streaming: false`
- `ssr: false` 的路由（已经是 SPA 渲染）
- 机器人和爬虫用户代理，即 `user-agent` 匹配 `botRegex` 的请求
- 预渲染的路由（`nuxt generate`）
- 来自插件、中间件或页面 setup 中的服务端 `navigateTo()` 重定向（只有在 `await` 解析之后才执行的页面 setup 重定向，可能出现在外壳刷新之后，此时它会在客户端水合期间发生）
- 初始渲染期间抛出的致命错误（在外壳刷新之前）
:::

:::warning
**响应状态码和头部必须在外壳刷新之前设置。** 流式传输会在第一个字节处提交 HTTP 状态码和头部，因此之后任何修改响应的操作都无法到达客户端。这是流式传输的固有特性，而不是 Nuxt 特有的 bug。

边界是外壳刷新：

- **能到达客户端**：来自 Nuxt 与 Nitro 插件以及路由中间件的修改——它们会在渲染开始前执行完毕——以及 `<script setup>` 中任何 `await` 之前的修改。
- **被丢弃**：在稍后的组件渲染期间（`<script setup>` 中 `await` 之后，或 `<Suspense>` 下的异步组件中）做出的 `setResponseStatus()`、`useResponseHeader()` 以及 h3 的 `setHeader()`/`appendResponseHeader()` 调用，因为这些工作可能在外壳已经上线后才发生。

要保留对响应的修改，请把它移入插件或路由中间件，或者让该路由退出流式传输：

- `routeRules: { '/path': { streaming: false } }`：静态的，按路由。
- 带 `ctx.prefersStream = false` 的 `render:route` 钩子：运行时的，按请求（例如，针对有条件设置 404 的路由）。

在开发模式下，流式处理程序会记录一个警告，指明被丢弃的修改和路由，因此这些永远不会静默失败。
:::

:::note
只有在外壳刷新之前被赋值的 `useCookie()` 才能到达客户端：即在插件中、在路由中间件中，或在 `<script setup>` 中任何 `await` 之前。更晚的赋值（例如在 `<Suspense>` 下的异步组件中）会被丢弃，并在开发模式下记录一条警告。在服务端 `navigateTo()` 之前，或在外壳刷新之前抛出的错误之前赋值的 cookie，会随着重定向或错误响应一起发送。
:::

:::note
如果在 HTTP 状态码已提交后，流式传输期间发生错误，会设置 `payload.error`，并且关闭标签仍会作为格式良好的文档发出，以便客户端在水合期间捕获错误并渲染错误页面。在外壳刷新之前抛出的错误会落到带有正确状态码的缓冲错误渲染器。
:::

:::note
**路由样式被流式传输，JS 提示仅限入口。** 外壳在路由渲染之前被刷新，因此它的 `<head>` 仅携带入口 chunk 的样式和提示。一旦渲染注册了页面和布局模块，它们的 CSS 会在外壳之后立即流式传输（当启用 `inlineStyles` 时内联为 `<style>`，否则为样式表链接），因此页面、布局和最顶层 async 组件的样式在 body 绘制之前到达（嵌套的 async 组件是 FOUC 注意事项，见下文）。路由特定的 JS chunk 不会从外壳预加载；浏览器在解析入口脚本后才会发现它们。流式传输改善了每个路由的 TTFB；LCP 收益在 JS 与入口 chunk 重叠的路由上最大。
:::

:::warning
**在外壳刷新之后注册的 head 标签会变成客户端补丁。** 渲染器会等待第一次渲染传递后才刷新外壳，因此在 `<script setup>`（任何 `await` 之前）、插件或中间件中同步调用的 `useHead`/`useSeoMeta` 仍会照常渲染进外壳的 `<head>`。更晚注册的标签（在 setup 中的 `await` 之后，或在嵌套的 `<Suspense>` 边界内）无法到达已经发出的 `<head>`；它们会以内联脚本的形式下发，在客户端修补 DOM。

执行 JavaScript 的客户端会应用这个补丁，而匹配 `botRegex` 的客户端根本不会被流式传输，因此它们收到的是完整的、经过缓冲的 `<head>`。除此之外任何一方（你的 `botRegex` 没有列出的爬虫、链接预览抓取器、`curl`）都完全看不到这些标签。JSON-LD 脚本、`noscript` 标签以及位于 body 中的标签是例外：它们会作为真实标记渲染在 `</body>` 之前，任何客户端都能读取。请把其它对 SEO 关键的标签（canonical 链接、社交元标签）保持为同步的，或者用 `routeRules: { '/path': { streaming: false } }` 让该路由退出流式传输。
:::

:::note
**组件 islands 与流式传输兼容。** Island 插槽内容和选择性客户端（`nuxt-client`）组件通常在渲染后的传递中被拼接进 HTML，一旦 body 流过 island 锚点，这就不可能了。相反，渲染器将每个 island teleport 作为惰性的 `<template>` 发出在文档末尾，并通过一个在水合前运行的内联脚本将其重定位到位。这对应用代码是透明的。例外是使用 `features.noScripts` 和 island 组件构建的应用，因为它们回退到缓冲渲染器，因为重定位脚本无法运行。
:::

### 模块钩子

模块通过现有的 `render:html` 钩子（现在第二个参数带有 `streaming: true` 标志）加上一个按请求的决策钩子和两个仅流式传输的钩子来参与流式响应：

- **`render:route`** 在渲染开始前每个请求触发一次，用于每次渲染（无论是否启用流式传输）。读取 `ctx.canStream` 以查看该路由是否可以流式传输，并设置 `ctx.prefersStream = false` 以强制对该请求使用缓冲渲染，例如基于 cookie、auth 状态或 A/B 桶。渲染器仅在 `canStream && prefersStream` 时流式传输。这是针对静态 `routeRules` / `botRegex` 配置的运行时逃生舱。
- **`render:html`** 在外壳刷新之前触发一次，其第二个参数带有 `streaming: true`。对 `htmlAttrs`、`head`、`bodyAttrs` 和 `bodyPrepend` 的修改会到达线上。对 `body`/`bodyAppend` 的修改被丢弃，因为 body 即将流式传输（会发出开发模式警告）。只修改 head 字段（CSP 注入、OG 标签、分析 meta）的模块在流式传输中无需代码更改即可工作。
- **`render:html:chunk`** 在渲染器生成的每个 chunk 入队之前触发。修改 `ctx.chunk: Uint8Array` 来转换字节（例如 nonce 注入）；读取 `ctx.index` 来区分第一个 chunk 与后续 chunk。
- **`render:html:close`** 在 body 流完成后、关闭标签之前触发。修改 `ctx.bodyAppend: string[]` 来注入最终的标记（body 末尾的分析标签、服务端渲染的调试小部件等）。

```ts
// modules/streaming-csp/src/runtime/server-plugin.ts
import { defineNitroPlugin } from '#imports'

export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('render:html', (ctx, { event }) => {
    const nonce = event.context.cspNonce
    if (!nonce) { return }
    // 对流式（外壳之前）和缓冲（渲染之后）两条路径都有效。
    for (let i = 0; i < ctx.head.length; i++) {
      ctx.head[i] = ctx.head[i].replace(/<script(?![^>]*\snonce=)/g, `<script nonce="${nonce}"`)
    }
  })
})
```

:::note
**CSP nonce。** 流式渲染器会发出几个绕过 unhead 的内联脚本和样式：引导队列、IIFE、suspense head 推送、island-teleport 重定位和路由 `<style>` 块。如果渲染的 head 脚本上存在 `nonce`，渲染器会自动在所有这些脚本上重用它，因此严格的 `script-src`/`style-src 'nonce-…'` 策略不会阻止流式传输。模块只需将 nonce 放在 head 脚本上（如上）；`render:html:chunk` 钩子仍可用于为你组件渲染进 body 的脚本打戳。
:::

:::warning
**SFC 样式的开发模式 FOUC：** 在开发模式下，Vite 将 SFC `<style>` 块作为 JavaScript 模块提供，这些模块在模块求值后客户端注入样式，外壳中没有对应的 `<link>`。通过流式传输，浏览器在那些样式注入模块运行之前就开始绘制流式 DOM，因此 SFC 定义的样式会短暂地无样式闪烁。

变通方法：将影响绘制的样式放在通过 `css: ['~/assets/main.css']` 注册的全局 CSS 文件中。全局 CSS 文件作为 `<link rel="stylesheet">` 发出在外壳的 `<head>` 中，并在 body 内容流式传输之前应用。对于不决定首次绘制的组件级样式，SFC `<style>` 块仍然没问题。

生产构建会把所有样式提取为真实的 CSS 文件（或通过 `features.inlineStyles` 内联），因此这只影响 `nuxt dev`。请对照 `nuxt build && nuxt preview` 来校验流式传输下的视觉效果。
:::

:::warning
**嵌套 async 组件的生产模式 FOUC：** 渲染器将路由 CSS 内联在 shell 之后立即发送的 chunk 中。它只能内联到此时已注册模块的组件的样式：页面、布局，以及直接放在 `<Suspense>` 边界内的任何 async 组件（Vue 在渲染开始时急切地实例化这些组件）。

一个渲染在*另一个 async 组件内部*的 async 组件，只有当其父级解析后才会被实例化，也就是在第一个 chunk 流式传输之后。它的 SFC `<style>` 会错过 shell 之后的样式 chunk，而是在关闭的 HTML 中发出，位于组件自身的 DOM 之后。浏览器会无样式地绘制该组件，直到最终的 chunk 到达。

通过以下方式避免：将影响绘制的样式排除在深层嵌套的 async 组件之外：

- 将影响绘制的样式放在全局 CSS 文件中（`css: ['~/assets/main.css']`）；这些会到达外壳的 `<head>`。
- 使用工具类（Tailwind、UnoCSS）样式化：工具类 CSS 存在于入口样式表中，而不是每个组件的 `<style>` 块中。
- 将拥有影响绘制的 `<style>` 的 async 组件直接放在 `<Suspense>` 边界下，而不是嵌套在另一个 async 父级之后。
- 或使用 `routeRules: { '/path': { streaming: false } }` 让该路由退出流式传输。

嵌套 async 组件上不影响绘制的 scoped 样式没问题：短暂的闪烁只对首屏内容有影响。
:::

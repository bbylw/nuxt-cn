Nuxt 可以使用不同的[服务端构建器](/docs/guide/going-further/builders)，即 Nitro 3（`nitro`，配合 Nuxt 5+）、Nitro 2（`nitropack`，配合 Nuxt 3/4），或者直接使用 Vite。

`nuxt/server` 的存在，是为了给不绑定某个特定服务端运行时的服务端代码提供与运行时无关的工具函数。它是 Nuxt 的第二个运行时入口，与 `nuxt/app`（也可以写作 `#app`）并列，后者面向你的应用中同样会在浏览器里运行的那一部分。

```ts [server/api/hello.ts]
import { defineHandler, getQuery } from 'nuxt/server'

export default defineHandler((event) => {
  const { name } = getQuery<{ name?: string }>(event)
  return { message: `Hello, ${name ?? 'world'}!` }
})
```

这段代码既可以运行在 `@nuxt/nitro-server` 之下，也可以运行在 `@nuxt/vite-server` 之下，并且在 h3 或 Nitro 升级大版本后仍能继续运行，因为 Nuxt 会在中心位置吸收这些变化。

`nuxt/server` 从 Nuxt 4.6 起提供，因此同一个文件可以同时服务于运行 `nitropack` v2 的 Nuxt 4.6、运行 Nitro v3 的 Nuxt 5，以及未来任何构建器带来的环境。

:::tip
每个 Nuxt 应用都安装了 `nuxt`，所以 `nuxt/server` 无需别名、无需新增依赖就能解析。从中导入的模块不需要对 h3 或 Nitro 的 peer 依赖。
:::

## 类型与工具函数

| 导入 | 用途 |
|---|---|
| `defineHandler` | 定义一个请求处理器。`defineEventHandler` 是它的别名，在 Nuxt 4.6 中同样可用。 |
| `createError`、`isNuxtError` | 构造并识别一个 HTTP 错误。 |
| `getRequestURL`、`getRequestHost`、`getRequestProtocol` | 请求的 URL、主机和协议。传入 `{ xForwardedHost: true, xForwardedProto: true }` 可以信任这些头部，但只应在你控制之下、会覆盖这些头部的代理后面这样做。 |
| `getRequestHeader`、`getRequestHeaders` | 读取请求头部。 |
| `getRouterParam`、`getRouterParams` | 读取为本次请求匹配到的动态片段。 |
| `getRequestIP` | 客户端 IP 地址，[转发头部的信任方式可按请求选择](#客户端-ip)。 |
| `getQuery`、`getValidatedQuery` | 读取查询字符串，可选地进行[校验](#校验)。 |
| `readBody`、`readValidatedBody` | 读取并解析请求体，可选地进行[校验](#校验)。 |
| `getCookie`、`parseCookies`、`setCookie`、`deleteCookie` | 读取单个或全部 cookie，以及写入 cookie。 |
| `setResponseStatus` | 设置响应状态码和原因短语。 |
| `handleCors` | 应用 [CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS) 头部并应答预检请求。 |
| `sendRedirect` | 重定向本次请求。 |
| `serverFetch` | 在进程内请求应用自己的一条路由，路径相对于 `app.baseURL`，并且除非设置了 `forwardHeaders`，否则会转发 `cookie` 和 `authorization` 头部。在没有进程内 fetch 的服务端构建器上它会拒绝执行。 |
| `useSession`、`getSession`、`updateSession`、`clearSession` | 读写一个[密封（seal）的会话 cookie](#会话)。 |
| `deriveSecret` | 从 `appSecret` [派生](#派生密钥)出的、面向特定用途的密钥。 |
| `getRouteRules`、`matchRouteRules` | 为本次请求，或为另一个路径匹配到的[路由规则](/docs/guide/concepts/rendering#route-rules)。 |
| `useRuntimeConfig` | 服务端的[运行时配置](/docs/guide/going-further/runtime-config)。 |
| `useServerHooks` | 服务端的运行时钩子：如 `render:html` 这样的渲染器钩子，以及在 `NuxtServerHooks` 上声明的那些钩子。 |
| `useAppConfig` | [应用配置](/docs/directory-structure/app/app-config)，在传入 event 时按每个请求返回一份副本。 |

类型与这些工具函数一同导出：`RequestEvent`、`RequestEventContext`、`NuxtRequestEvent`、`EventHandler`、`AppRouteRules`、`ServerRoutes`、`CorsOptions`、`ValidateResult`、`NuxtError`、`NuxtErrorDetails`、`NuxtErrorJSON`、`NuxtErrorLike`、`Session`、`SessionConfig`、`SessionData`、`SessionEvent`、`SessionManager`、`SessionPassword` 和 `SessionUpdate`。

除 `useAppConfig` 之外，这些名称在服务端代码中都是[自动导入](/docs/directory-structure/server)的，因此上面那条导入语句是可选的。写出它可以让文件在关闭了服务端自动导入的项目中依然工作，也是模块应当采用的做法。

:::tip
`defineHandler` 会保留你的处理器的返回类型，正是它决定了 [`$fetch` 和 `useFetch`](/docs/getting-started/data-fetching) 调用该路由时的类型，以及对该路由调用 `serverFetch` 时 `response.json()` 的类型。请为你返回的值标注类型，而不是为处理器标注。
:::

## 事件

`RequestEvent` 是 `nuxt/server` 工具函数所操作的事件，其中包含请求本身、它的 URL、将要发送的响应，以及请求上下文。

```ts
interface RequestEvent {
  readonly req: Request
  url: URL
  readonly res: { status?: number, statusText?: string, readonly headers: Headers }
  readonly context: RequestEventContext
}
```

要设置、读取、追加或移除响应头部，直接使用 `event.res.headers`：它是一个标准的 `Headers` 对象。

Nitro 会在其上追加更多内容，例如 `event.node`、`event.runtime` 和 `event.waitUntil()`，但上面这四个核心属性在所有运行时中都可用，并且不需要任何辅助函数：

```ts [server/api/echo.post.ts]
import { defineHandler } from 'nuxt/server'

export default defineHandler(async (event) => {
  const { id } = await event.req.json()
  return { id, page: event.url.searchParams.get('page') }
})
```

`NuxtRequestEvent` 是同一个请求，其形状由所配置的构建器提供；在 `@nuxt/nitro-server` 下它就是 h3 的 `H3Event`。

## 处理器

处理器文件必须从 `nuxt/server` 默认导出 `defineHandler`（或其别名 `defineEventHandler`）的结果。若是一个裸函数，或者是由 h3 自己的 `defineHandler` 包装过的函数，那么它收到的将是服务端运行时自身的事件。

处理器可以返回：

- 一个可 JSON 序列化的值，以 JSON 发送，并带上在 `event.res` 上设置的状态码和头部。
- 一个 `Response`，用它自身的状态码发送。在 `event.res.headers` 上设置的头部会被追加到它上面，并替换同名的头部；只有 `set-cookie` 例外，它会被追加。
- 一个 `ReadableStream`，作为响应体流式发送。

## 校验

`readValidatedBody` 和 `getValidatedQuery` 接受任意 [Standard Schema](https://standardschema.dev)（Zod、Valibot、ArkType 及其它），也接受一个函数——该函数返回校验后的值，或返回 `true` 接受输入、`false` 拒绝输入。

```ts [server/api/users.post.ts]
import { defineHandler, readValidatedBody } from 'nuxt/server'
import { z } from 'zod'

export default defineHandler(async (event) => {
  const user = await readValidatedBody(event, z.object({ name: z.string() }))
  return { created: user.name }
})
```

无效的输入会被拒绝，返回一个 `400`，其 `data.issues` 列出失败的项目。传入 `onError` 可以用另一个错误来拒绝它。

## 客户端 IP

`getRequestIP(event)` 返回服务端运行时就该连接报告的地址，如果它没有报告任何地址则返回 `undefined`。默认不信任任何转发头部，因为客户端可以在其中发送任意值。

在你控制之下的代理后面，可以传入 `{ xForwardedFor: true }` 来改为读取 `X-Forwarded-For` 的第一项。只有当代理会覆盖该头部时才这样做：一个只是追加值的代理会让客户端发送的那一项排在最前面。

## 会话

`useSession` 读取本次请求的会话，并在无可读取内容时把一个新的会话密封进 cookie。数据是用 [iron](https://github.com/brc-dd/iron-webcrypto) 密封的，因此它保存在 cookie 中而不是服务端存储里，并且 cookie 默认为 `httpOnly`、`secure`、`sameSite: 'lax'` 和 `path: '/'`。

```ts [server/api/visits.ts]
import { defineHandler, useSession } from 'nuxt/server'

export default defineHandler(async (event) => {
  const session = await useSession<{ visits: number }>(event)
  await session.update(data => ({ visits: (data.visits ?? 0) + 1 }))
  return { visits: session.data.visits }
})
```

没有 `password` 时，会话使用从应用的 [`appSecret`](/docs/guide/going-further/runtime-config#application-secret) 派生出的密钥来密封，所以唯一需要设置的就是 `NUXT_APP_SECRET`。传入一个至少 32 个字符的 `password`，可以改为使用你自己的密钥来密封。设置 `maxAge`（以秒为单位）会让 cookie 和被密封的值一同过期，`name` 用于把 cookie 名称从 `nuxt-session` 改成别的，`cookie` 用于覆盖任意 cookie 属性。

每个请求只会解封一次会话，所以你可以从任意多的地方调用 `getSession`。`updateSession` 和 `clearSession` 是不带管理器对象的同一组操作。

### 派生密钥

`deriveSecret(purpose)` 会从 `appSecret` 为某一个用途解析出一个密钥：32 字节、十六进制编码，只要 `appSecret` 不变它就保持稳定，并且每个用途都各不相同。会话辅助函数用的就是它，模块也应当用它来代替向用户索要自己的密钥。请给用途加上属于谁的命名空间。

```ts
import { deriveSecret } from 'nuxt/server'

const password = await deriveSecret('my-module:tokens')
```

当 `appSecret` 未设置或长度少于 32 个字符时，它会抛出一个点名 `NUXT_APP_SECRET` 的 `500` 错误。

:::note
h3 自带同名的会话辅助函数，可以通过 `import { useSession } from 'nitro/h3'` 访问。它们是另一套独立实现，与这里的这些不能互换：它们默认使用 `h3` 而不是 `nuxt-session` 作为 cookie 名称，有各自的配置，而且其中一个所签发的会话无法用另一个解封。
:::

:::note
会话 API 是稳定的，但被密封 cookie 的格式可能会在次版本中变化：一旦 `iron-webcrypto` 发布基于 AES-GCM 的密封实现，Nuxt 就计划切换到它。届时已有的会话会按旧格式读取，并在下一次写入时以新格式重新密封，因此用户不会被登出。被密封的值与 h3 的 `useSession` 所产生的并不互换。
:::

:::warning
会话随 cookie 传输，因此它受浏览器所能接受的规模限制。写入一个序列化后超过 4096 字节的会话会抛出错误；请把大数据留在服务端，并在会话中通过 id 引用它。
:::

## 超出该入口范围的能力

`nuxt/server` 并不是 h3 的重新导出，所以如果你需要 h3 和 Nitro 提供的其它东西，例如服务端生命周期（`definePlugin` 和 `defineErrorHandler`）或 Nitro 自身的运行时钩子，你就需要直接导入它们。

这些辅助函数中的大多数都直接接受原样的 event：

```ts [server/api/upload.post.ts]
import { defineHandler } from 'nuxt/server'
import { readMultipartFormData } from 'nitro/h3'

export default defineHandler(async (event) => {
  const parts = await readMultipartFormData(event)
  return { received: parts?.length ?? 0 }
})
```

对于只读取请求的任意 h3 辅助函数，例如 `readRawBody`、`readFormData`、`readMultipartFormData` 和 `assertMethod`，这样做都是可行的。

对于需要运行时自身事件的处理器，例如调用了 `proxy`、`proxyRequest`、`fetchWithEvent` 或 `writeEarlyHints`，或读取了 `event.node`、`event.waitUntil()`、`event.runtime` 的处理器，请在这一个处理器上从 `nitro/h3` 导入 `defineHandler`：

```ts [server/api/proxy.ts]
import { defineHandler, proxyRequest } from 'nitro/h3'

export default defineHandler(event => proxyRequest(event, 'https://example.com'))
```

一个文件可以同时从 `nitro/*` 和 `nuxt/server` 导入。那样它就只能运行在 Nitro v3 上，因此模块应把它注册为自己的 `nitro3` 变体。

Nitro 自己的 API 大多完全不接受 event：`getRouteRules(method, pathname)`、`defineCachedHandler()`、`useKV()`、`useDatabase()` 以及任务（task）。

## 不可移植的部分

以下几个方面意味着要走到 `nuxt/server` 之外，因为 Nuxt 无法为每个构建器提供它们：

- **存储（Storage）。** `useKV()` 来自 `nitro/kv`，它背后的驱动配置也一样。
- **缓存。** `defineCachedHandler()` 和 `defineCachedFunction()` 来自 `nitro/cache`。需要到处都能工作的缓存，就直接依赖某个缓存库。
- **服务端插件。** `definePlugin()` 来自 `nitro`。只注册渲染钩子的模块可以改为注册一个[渲染器插件](/docs/guide/modules/server-compatibility#renderer-plugins)，它在任何服务端构建器下都会运行。在插件内部，来自 `nuxt/server` 的 `useServerHooks()` 用于注册渲染器钩子（包括 `render:html`）以及在 `NuxtServerHooks` 上声明的那些钩子；Nitro 自身的钩子，例如 `request`、`response` 和 `error`，来自 `nitro/app` 中的 `useNitroHooks()`。
- **惰性处理器。** `lazyEventHandler()` 来自 `nitro/h3`。
- **任务。** `defineTask()` 和 `runTask()` 来自 `nitro/task`。

## 仅限服务端代码

从 Vue 组件、插件或 `shared/` 目录中导入 `nuxt/server` 会让构建失败，并且错误会转而把你指向 `#app`、`#imports`、`$fetch` 和 `useFetch`。它的类型在这些上下文中仍然可以解析，这正是让 `$fetch` 知道你的服务端路由返回什么的方式。

`nuxt/server` 也只在由服务端构建器打包的代码中有效，因为构建器会在它背后提供运行时配置、应用配置、钩子以及进程内 fetch。运行在 Nuxt 进程中的代码，例如 `nuxt.config.ts`、模块的 `setup`，或传给 `addDevServerHandler` 的函数，都没有这些东西，所以在这些地方不要导入 `nuxt/server`：例如 `useRuntimeConfig()` 和 `useAppConfig()` 会返回空对象。请改为读取 `nuxt.options`，并在[开发服务端处理器](/docs/guide/modules/server-compatibility#dev-server-handlers)中了解如何在模块里编写处理器。

## 模块

一个运行时代码只从 `nuxt/server` 导入的模块，从 v4.6 起可以在任何服务端构建器下运行，无需版本检查，也不依赖 h3 或 Nitro：

```ts [runtime/server/api/status.ts]
import { defineHandler, useRuntimeConfig } from 'nuxt/server'

export default defineHandler(() => ({
  version: useRuntimeConfig().myModule.version,
}))
```

:::tip
打包时请把 `nuxt/server` 保留为 external；它会在 Nuxt 构建中被解析到正确的那个服务端构建器工具集。
:::

要支持 `<4.6` 的 Nuxt 版本还需要多一步，因为那些项目中并没有可供解析的 `nuxt/server`。你可以改为并排注册这个可移植的文件和你今天所交付的那个文件，由 Nuxt 挑选应用能够运行的那一个。

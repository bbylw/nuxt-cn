---
title: "服务端兼容性"
description: "交付同一个模块，无论底下是哪个服务端运行时，都能同时服务 Nuxt 4 和 Nuxt 5。"
---

Nuxt 支持多种服务端运行时。Nuxt 3 和 4 的目标是 Nitro v2（`nitropack`），它使用 `h3` v1；Nuxt 5 默认使用 Nitro v3（`nitro`），它使用 `h3` v2。此外，用户也可以使用基于 Web API、到处都兼容的自定义服务端运行时（`nuxt/server`）。

为了协助从 Nuxt 4 升级，为 Nitro v2 编写的模块代码可以继续通过一个临时的兼容层运行。本指南介绍这个兼容层为你做了什么，以及如何迁移到对 Nuxt 4 和 5 的完整支持。

:::note
如果你的模块没有服务端代码，这里的内容都不适用于你。
:::

## 兼容层

当模块的服务端代码从 `h3`、`nitropack`、`nitropack/runtime`、`#internal/nitro` 或 `#imports` 导入时，它就进入了兼容层。（导入 `nuxt/server` 或 `nitro/*` 的文件不会被改动。）

在这个兼容层内部，`h3` 会解析到一个建立在 h3 v2 之上的 h3 v1 辅助函数接口，`nitropack` 系列说明符会解析到它们的 Nitro v3 等价物，`useRuntimeConfig(event)` 保持它的按请求行为，并且我们会注入 v1 代码可能会读取的 `event.node`、`event.context.nitro` 和 `event.context._nitro.routeRules` 形状。

为了帮助迁移，Nuxt 会记录它把兼容层应用到了哪些模块：

```text
WARN [NUXT_B9003] Nitro v2 compatibility was applied to server code from 2 modules, because of what it imports:
  - @nuxtjs/robots (imports `h3`, `nitropack/runtime`, `#imports`)
  - nuxt-site-config (imports `h3`, `nitropack/runtime`)
```

:::note
兼容层覆盖的是你自己的代码所导入的说明符。它不会提供 `nitropack` v2 恰好被提升（hoist）进服务端 bundle 的那些包，例如 `lru-cache` 之类的。请务必在 `package.json` 中声明你模块的依赖。
:::

## 推荐的迁移方式

[`nuxt/server`](/docs/guide/going-further/server-imports) 是编写基于 Web API、与运行时无关的服务端代码的导入入口，它随 Nuxt 4.6+ 提供。用它编写的代码可以运行在 `nitropack` v2 上、Nitro v3 上，以及其他服务端构建器（例如 `@nuxt/vite-server`）之下。

### 事件处理器

如果你正在注册事件处理器，请保留你现有的处理器（以兼容 Nuxt `<4.6`），并在它旁边用 `nuxt/server` 新增一个可移植的处理器，把两者都注册上。Nuxt 会注册应用能够运行的那个实现：在 Nitro v3 和其它构建器下使用可移植文件，在仍运行 `nitropack` v2 的宿主上使用 v2 文件。

```ts [module.ts]
import { addServerHandler, createResolver, defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule({
  meta: { name: 'my-module' },
  setup () {
    const { resolve } = createResolver(import.meta.url)

    addServerHandler({
      route: '/api/my-module/status',
      handler: {
        nuxt: resolve('./runtime/server/status'),
        nitro2: resolve('./runtime/server/status.legacy'),
      },
    })
  },
})
```

这两个文件的差异在于它们的导入，以及处理器用到 `nuxt/server` 处理方式不同的某个 h3 v1 辅助函数或行为的地方：

:::code-group

```ts [runtime/server/status.ts]
import { defineEventHandler, useRuntimeConfig } from 'nuxt/server'

export default defineEventHandler(() => ({
  version: useRuntimeConfig().public.myModule.version,
}))
```

```ts [runtime/server/status.legacy.ts]
// @ts-expect-error `#imports` 的类型是为应用准备的，不是为服务端构建
import { useRuntimeConfig } from '#imports'
import { defineEventHandler } from 'h3'

export default defineEventHandler(event => ({
  version: useRuntimeConfig(event).public.myModule.version,
}))
```

:::

:::read-more{to="/docs/getting-started/upgrade#differences-from-h3-v1"}
查看 h3 v1 与 `nuxt/server` 之间的所有差异，以及应当改用什么。
:::

各个键表明该文件依赖哪个服务端 API：

| 键 | 该文件导入 | 运行位置 |
|---|---|---|
| `nuxt` | 只有 `nuxt/server` | 任何服务端构建器，从 Nuxt 4.6 起 |
| `nitro2` | `h3`、`nitropack/runtime`、`#imports` | 直接在 `nitropack` v2 上；在 Nitro v3 上通过兼容层 |
| `nitro3` | `nitro`、`nitro/h3`，单独使用或与 `nuxt/server` 一起 | Nitro 服务端构建器，v3 |

Nuxt 会根据用户所使用的服务端构建器挑选最合适的那个处理器。如果你注册的处理器是用户的服务端构建器无法运行的，它会被跳过并给出警告。

:::tip
只在代码需要 Nitro v3 独有的 API 时才使用 `nitro3`。使用 `nuxt/server` 会让你的代码在将来更具可移植性。
:::

采用这种模式意味着你同时支持旧版（`<4.6`）和新版 Nuxt（包括 Nuxt 5）。

:::important
`handler` 的对象形式需要在你模块的 `dependencies` 中提供 `@nuxt/kit@^4.6`，这也是[模块起手式](/docs/guide/modules/getting-started)所做的配置。如果 `@nuxt/kit` 只是一个 `devDependency` 并在构建时保持 external，或者它是一个 `peerDependency`，那么实际运行的将是应用自己的版本，而 4.6 之前的版本会在对象形式的 `handler` 上失败。
:::

要对 `nuxt` 文件做类型检查，请把 `nuxt@>=4.6` 安装为 `devDependency`。要对 `nitro3` 文件做类型检查，还需要安装 `nitro`。

如果你模块自身的别名在两个 Nitro 大版本上已经能解析到正确的代码，请为两个键注册同一个文件（`{ nitro2: file, nitro3: file }`），或者设置 [`meta.compatibility.server`](#声明无法推断的部分)。

在 `nitropack` v2 宿主上，Nuxt 优先选择 `nitro2` 变体，因此只有当 `nuxt` 变体是唯一被注册的变体时，它才会在那里运行。请在 Nuxt 5 上测试 `nuxt` 变体。

在 Nuxt 5 的 playground 和测试 fixture 中，h3 那个被自动导入的 `defineEventHandler` 并不可用：请从 `nuxt/server` 导入它。

### 开发服务端处理器

`addDevServerHandler` 接受同样的这些键，但每个变体都是你模块代码中的一个函数，它运行在 Nuxt 进程里而不是服务端构建里。`nuxt/server` 是[仅限服务端代码](/docs/guide/going-further/server-imports#server-code-only)的，因此不要在模块代码中导入它，即使惰性导入也不行。

请改为针对 Web 的 `Request` 和 `Response` 编写处理器，在 `setup` 中从 `nuxt.options` 读取配置，并让它适配各个服务端 API：

```ts [module.ts]
import { addDevServerHandler, defineNuxtModule } from '@nuxt/kit'
import { defineEventHandler, toWebRequest } from 'h3'

export default defineNuxtModule({
  meta: { name: 'my-module' },
  setup (_options, nuxt) {
    const greeting = nuxt.options.runtimeConfig.public.myModule.greeting

    function greet (request: Request) {
      const name = new URL(request.url).searchParams.get('name')
      if (!name) {
        return new Response('Missing name', { status: 400 })
      }
      return Response.json({ message: `${greeting}, ${name}!` })
    }

    addDevServerHandler({
      route: '/_my-module/greet',
      handler: {
        nuxt: event => greet(event.req),
        nitro2: defineEventHandler(event => greet(toWebRequest(event))),
      },
    })
  },
})
```

`nuxt` 变体收到的是一个 `RequestEvent` 并读取它的 `event.req`；`nitro2` 变体用 `toWebRequest()` 转换 h3 v1 的事件。由于该模块导入了 `h3` v1，请把 `h3@^1` 加入你模块的 `dependencies`。

开发处理器的路由并不会在每个服务端 API 上匹配相同的路径。`nuxt` 和 `nitro3` 变体会精确匹配该路由。`nitro2` 处理器则像 Nitro v2 那样把它当作路径前缀来匹配，因此 `/_my-module` 也会匹配 `/_my-module/inter.woff2`。Nuxt 会把单个函数当作 `nitro2` 处理器。

要让所有变体都提供某个路由之下的路径，请把路由以 `/**` 结尾：

```ts [module.ts]
addDevServerHandler({
  route: '/_my-module/assets/**',
  handler: {
    nuxt: event => serveAsset(event.req),
    nitro2: defineEventHandler(event => serveAsset(toWebRequest(event))),
  },
})
```

这里的 `serveAsset` 接受一个 `Request` 并返回一个 `Response`，与上一个例子中的 `greet` 相同。该路由会匹配 `/_my-module/assets` 以及它之下的每条路径，因此你不需要再额外注册基础路径。在 `nitropack` v2 宿主上，这需要你模块的 `dependencies` 中有 `@nuxt/kit@^4.6.1`。

`nitro2` 处理器读取的 `event.path` 是相对于其路由基础的，因为 Nitro v2 会把基础部分剥掉。对于一条到 `/_my-module/assets/inter.woff2` 的请求，`event.path` 是 `/inter.woff2`。完整 URL 仍可通过 `toWebRequest()` 获得，而 `nuxt` 变体从 `event.req.url` 读取它。

### 服务端工具函数

如果你的模块导出了接收 event 的工具函数（通过别名、`addServerImports` 或类型模板），请把参数类型标注为来自 `nuxt/server` 的 `RequestEvent`，或标注为它实际读取的那部分，例如 `Pick<RequestEvent, 'req' | 'context'>`。标注为 `H3Event` 的参数只接受某一个 h3 大版本的事件，因此该工具函数无法从 `nuxt/server` 处理器中调用。

`getNitroVersion` 报告的是 Nitro 的大版本，而不是宿主运行的是哪个服务端 API：一个 `server.builder` 不同的宿主不会运行其中任何 Nitro 相关的能力。

### 渲染器插件

如果你的模块注册渲染钩子，例如用 `render:html` 往每个页面的 `<head>` 里加入一段脚本，请改用 `addRendererPlugin` 注册一个渲染器插件。每个 SSR 渲染器都只调用它一次，在渲染之前，并把渲染期间要调用的钩子交给它。它在任何服务端构建器下、在服务端渲染所处的任何运行时中都会运行，包括 Cloudflare Workers 这样的部署目标。

:::code-group

```ts [module.ts]
import { addRendererPlugin, createResolver, defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule({
  meta: { name: 'my-module' },
  setup () {
    const { resolve } = createResolver(import.meta.url)

    addRendererPlugin(resolve('./runtime/server/renderer'))
  },
})
```

```ts [runtime/server/renderer.ts]
import type { RendererPlugin } from 'nuxt/server'

export default (({ hooks }) => {
  hooks.hook('render:html', (html) => {
    html.head.push('<meta name="my-module" content="enabled">')
  })
}) satisfies RendererPlugin
```

:::

该插件可以注册 `render:route`、`render:html`、`render:html:chunk`、`render:html:close`、`render:document` 和 `render:island`。`render:route` 和 `render:html` 会对渲染器产出的每个页面调用，包括错误页面和带有 `ssr: false` 路由规则的路由；`render:html:chunk` 和 `render:html:close` 只对流式响应调用；`render:document` 只对非流式响应调用；`render:island` 则针对服务端组件调用。它们每个都在服务端运行时上注册的同名钩子（例如由 Nitro 插件注册的）之前被调用。该插件是同步调用的，它返回的 promise 不会被等待。

没有 `render:response` 钩子。要为某个页面设置响应头部，请在 `render:html` 中设置 `event.res.headers`，它在响应被创建之前调用。

一个需要处理整个页面的模块（例如内联关键 CSS）可以注册 `render:document`。它在每个 `render:html` 处理函数（包括在服务端运行时上注册的那些）都执行完毕之后，带着序列化好的 HTML 文档被调用，并且响应会由它留下的 `html` 构建而成。

```ts [runtime/server/renderer.ts]
import type { RendererPlugin } from 'nuxt/server'

export default (({ hooks }) => {
  hooks.hook('render:document', (document) => {
    document.html = document.html.replace('</body>', '<script src="/my-module.js"></script></body>')
  })
}) satisfies RendererPlugin
```

在还没有渲染器插件的 Nuxt 版本上，`addRendererPlugin` 会把同一个文件注册为 Nitro 插件，这需要你模块的 `dependencies` 中含有带 `addRendererPlugin` 的 `@nuxt/kit`。Nitro 会带着它的 app 调用该文件，而 app 的 `hooks` 正是渲染器会调用的那些，因此只要插件只读取 `hooks`、只注册那个版本会调用的钩子，并且不导入那个版本的服务端无法解析的东西，它在那里同样有效。如果做不到，请改为传入要注册的 Nitro 插件：

```ts [module.ts]
addRendererPlugin({
  nuxt: resolve('./runtime/server/renderer'),
  nitro2: resolve('./runtime/server/plugin.legacy'),
})
```

没有渲染器插件的 Nuxt 版本不会调用 `render:document`。在 Nitro v2 上，`render:response` 钩子会以完成的文档作为 `response.body` 被调用。

:::note
用 `@nuxt/vite-server` 构建的静态 SPA（`ssr: false`）没有服务端，因此它的文档是作为一条预渲染路由，通过渲染器插件的 `render:html` 和 `render:document` 钩子渲染的：每次构建一次，针对基础 URL，并带有设置好的 `import.meta.prerender`。这些钩子添加的内容对每位访客都相同。在开发模式下，文档会为每次导航渲染一次。不会为它调用其它渲染器钩子。
:::

### 服务端插件

服务端插件也接受各个变体，尽管它们是 Nitro 专有的，所以没有可供注册的通用 `nuxt` 变体。只注册渲染钩子的插件可以改用[渲染器插件](#渲染器插件)。

:::tip
由于来自 `nitro` 的 `definePlugin()` 和来自 `nitropack/runtime` 的 `defineNitroPlugin()` 都是恒等函数，你可能可以把它们替换成一个类型标注，从而写出同时对 `nitro2` 和 `nitro3` 都可移植的代码。
:::

```ts [module.ts]
import { addNitroPlugin, createResolver, defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule({
  meta: { name: 'my-module' },
  setup () {
    const { resolve } = createResolver(import.meta.url)

    addNitroPlugin({
      nitro3: resolve('./runtime/server/plugin'),
      nitro2: resolve('./runtime/server/plugin.legacy'),
    })
  },
})
```

### 其它变体

对于其它任何指向服务端代码的东西，例如别名、类型模板，或读取服务端事件的 app 插件，你可以使用 `resolveServerVariant` 来解析出适用于当前 Nuxt 版本的那个变体；如果一个都跑不了，它返回 `undefined`。

`addServerImports` 在 `from` 中接受同样的这些变体。

```ts [module.ts]
import { addServerImports, createResolver, defineNuxtModule, resolveServerVariant } from '@nuxt/kit'

export default defineNuxtModule({
  meta: { name: 'my-module' },
  setup (_options, nuxt) {
    const { resolve } = createResolver(import.meta.url)

    const someServerFile = resolveServerVariant({
      nuxt: resolve('./runtime/server'),
      nitro2: resolve('./runtime/server.legacy'),
    })

    if (someServerFile) {
      nuxt.options.alias['#my-module/server'] = someServerFile
    }

    addServerImports({
      name: 'verifyToken',
      from: { nuxt: resolve('./runtime/verify'), nitro2: resolve('./runtime/verify.legacy') },
    })
  },
})
```

在 `nitropack` v2 下运行时，`nitro2` 总是优先于 `nuxt`；在 `nitro` v3 下运行时，`nitro3` 总是优先于 `nuxt`。因此，如果你需要测试 `nuxt` 变体，请在测试 fixture 中把 `server.builder` 设为一个非 Nitro 的构建器，例如 `@nuxt/vite-server`。

### 声明无法推断的部分

Nuxt 会读取每个被注册的文件以及它所导入的文件里的 import，以此判断它使用的是哪个 API，所以你无需自己声明兼容性。纯类型导入（`import type`）会被忽略，你的 runtime 目录中没有任何被注册文件导入的文件也会被忽略。但如果这还不够，你可以设置 `meta.compatibility.server`：

```ts [module.ts]
export default defineNuxtModule({
  meta: {
    name: 'my-module',
    compatibility: { server: 'nuxt' },
  },
})
```

如果我们无法判断，代码会被当作 `nitro2` 处理。

Nuxt 读取的是你模块自己文件的 import，而不是它们所调用的那些包的 import。一个调用了内部导入 Nitro 的库的 `nuxt` 文件会被接受，但在 Nitro 之外的构建器下会失败。

### 为运行时配置和事件标注类型

要为你模块添加的运行时配置键标注类型，请增强来自 `nuxt/schema` 的 `RuntimeConfig`（或 `PublicRuntimeConfig`）。这样这些键在 `nuxt`、`nitro2` 和 `nitro3` 文件中都会被正确推导。

这样的增强只改变类型。环境变量会[被转换为默认值的类型](/docs/guide/going-further/runtime-config#environment-variables)，所以请给每个键一个与你所增强类型一致的默认值，或者在 [`updateRuntimeConfig()`](/docs/api/kit/runtime-config#schemas) 中用 schema 声明它。

```ts [module.ts]
declare module 'nuxt/schema' {
  interface RuntimeConfig {
    myModule: { apiKey: string }
  }
}
```

构建器专有的类型，例如 `useRequestEvent()` 的 `H3Event`，或 `nitro:config` 钩子中的完整 Nitro 配置，来自生成的 `.nuxt/nuxt.d.ts`。没有它时，它们会解析为与构建器无关的类型（`RequestEvent` 和一个精简版的 Nitro 配置）。请把接受 event 的工具类型针对 `RequestEvent` 来标注，以支持任何服务端构建器。

### 插件、存储与缓存

一个建立在 Nitro 插件、存储或缓存之上的模块没有 `nuxt` 变体，因为 `nuxt/server` 并不覆盖这些领域。请现在把它的文件注册为 `nitro2`，并在移植它们时补上 `nitro3` 变体。

## Nitro 专有代码

`nuxt/server` 覆盖的是请求与响应相关的工作：处理器、错误、路由参数、查询与请求体的读取和校验、头部、CORS、cookie、会话、重定向、路由规则、运行时配置、应用配置、用 `serverFetch()` 进行的进程内 fetch，以及用 `useServerHooks()` 提供的运行时钩子。但 Nitro 覆盖的范围远不止这些，因此如果你需要下面这些领域，你可能得在 `nitro2` 或 `nitro3` 文件里继续使用 Nitro 自己的导入。

请使用该文件所对应版本的说明符。一个导入 `nitro/*` 的文件会被读作 Nitro 3 代码，因此 `nitro2` 文件必须改为导入 `h3` 和 `nitropack/*`：

| 领域 | 在 `nitro3` 文件中 | 在 `nitro2` 文件中 |
| --- | --- | --- |
| 存储：`useKV()`（在 Nitro v2 中是 `useStorage()`）及其驱动配置 | `nitro/kv` | `nitropack/runtime` |
| 缓存：`defineCachedHandler()`、`defineCachedFunction()` | `nitro/cache` | `nitropack/runtime` |
| 服务端插件 | 来自 `nitro` 的 `definePlugin()` | 来自 `nitropack/runtime` 的 `defineNitroPlugin()` |
| Nitro 自身的运行时钩子，例如 `request`、`response` 和 `error` | 来自 `nitro/app` 的 `useNitroHooks()` | 来自 `nitropack/runtime` 的 `useNitroApp().hooks` |
| 惰性处理器：`lazyEventHandler()` | `nitro/h3` | `h3` |
| 任务：`defineTask()`、`runTask()` | `nitro/task` | `nitropack/runtime` |

:::read-more{to="/docs/guide/going-further/server-imports#reaching-past-the-surface"}

:::

## Nitro 的重要变化

以下行为在 Nitro v3 中发生了变化，可能需要你在代码中做进一步更新：

- **带路由的中间件不再为子路径运行。** `nitropack` v2 挂载带 `route` 的中间件时，会让它对该路由*及其之下*的所有路径（例如 `/path/subpath`）运行，并把该路由前缀从 `event.path` 中剥掉。Nitro v3 则像对待其它处理器一样精确匹配它。更新时，如果你打算两者都覆盖，请把 `route` 放宽为 `/path/**`，并从 `event.path` 读取完整路径。
- **未带 `route` 注册的处理器相当于全局中间件。** Nitro v3 要求提供路由。如果你需要中间件，请用 `middleware: true` 加一条显式路由来注册它，即使它打算在所有路径 `/**` 上运行。
- **`beforeResponse` 和 `afterResponse` 不是 Nitro v3 的钩子。** 它们在兼容层中仍然有效，但你应当改用 `response` 钩子，它会收到构建好的 `Response`。请注意，即便有兼容层，替换 `response.body` 的钩子，或在流式传输时读取它的钩子，都是不被支持的。
- **Nitro 3 中没有 `globalThis.$fetch`。** 对于应用自身的一条路由，请使用来自 `nuxt/server` 的 `serverFetch(event, path)`。你也可以使用 `event.$fetch`，或从 `#imports/server` 导入 `$fetch`。
- **`import.meta.url` 不再是服务端入口。** Nitro v2 会把它改写为一个指向入口的全局变量，而 Nitro v3 会输出真实的值。请改为从一个你能控制的路径解析资源。

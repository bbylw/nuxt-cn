`@nuxt/cli` 就是 `nuxt` 命令：它启动开发服务器、为你的应用构建生产版本、搭建文件脚手架、管理模块，并且回答有关你项目的问题。它是 `nuxt` 的一个依赖，因此任何 Nuxt 项目都已经包含了它。

```bash [Terminal]
npx nuxt dev
```

该可执行文件安装为 `nuxt`，同时为了兼容较早的项目设置，也安装为 `nuxi`、`nuxi-ng` 和 `nuxt-cli`。为新项目搭建脚手架由一个独立的包 [`create-nuxt`](/docs/api/commands/init) 负责，这样即使没有可装入的项目也能运行它。

`nuxi` 是第三个包：一个没有任何依赖的独立 CLI，用于在项目之外运行命令或进行全局安装。

## 环境要求

CLI 运行在 Node v22.21+、v24.11+ 或 v26+ 之上，并在这些版本中原生导入 TypeScript 配置。不支持 Nuxt 2 和 `@nuxt/bridge`。

## 运行命令

在项目内部，你的包管理器会运行项目所依赖的那个版本：

```bash [Terminal]
pnpm nuxt dev
npm exec nuxt dev
yarn nuxt dev
bun nuxt dev
```

在项目之外或以全局方式安装时，`npx nuxi` 可以运行同样的命令。当项目中安装了 `@nuxt/cli` 时，它会把每个命令交给项目中的那一份去执行，因此实际运行的代码与它所依附的 Nuxt 版本相匹配，而不是你机器上恰好存在的任意版本。当项目中没有 CLI、项目中的版本早于 v3.26，或者项目中的版本不认识该命令时，它会退回到自身内置的命令，因此锁定在旧版本发布上的项目依然能够使用更新的命令。

## 全局选项

`--cwd` 既可以写在命令名之前，也可以写在其后，这在 monorepo 中很有用：

```bash [Terminal]
npx nuxt --cwd apps/web dev
```

对于接受 `ROOTDIR` 位置参数的命令，显式传入的 `--cwd` 会被视为对它的覆盖。对任意命令使用 `--help` 都会打印它的参数与选项，`--version` 则打印 CLI 版本。

## 拼错的命令与标志

无法识别的命令会与已有的命令进行匹配，无法识别的标志则会与该命令声明的标志进行匹配。在交互式终端中，它会向你提供修正后的写法供你选择执行；其他情况下则以警告形式报告，这样拼错的标志不再看起来像一个只是没有生效的标志。

## 项目命令

如果某个命令不是 CLI 自身提供的，就会在你的项目中按 `nuxt-<command>` 可执行文件去查找，因此一个依赖也可以添加自己的命令。[`nuxt build-module`](/docs/api/commands/build-module) 就是这样工作的：它运行由 `@nuxt/module-builder` 安装的 `nuxt-build-module` 可执行文件。

## Shell 补全

`nuxt complete <shell>` 会打印一份补全脚本，其能力由 [`@bomb.sh/tab`](https://github.com/bombshell-dev/tab) 提供。它会补全命令、标志以及部分标志取值：`nuxt dev` 的端口与主机、`nuxt build --preset` 的 Nitro 预设，以及日志级别。

::code-group

```bash [zsh]
npx nuxt complete zsh > "${fpath[1]}/_nuxt"
```

```bash [bash]
npx nuxt complete bash > /etc/bash_completion.d/nuxt
```

```bash [fish]
npx nuxt complete fish > ~/.config/fish/completions/nuxt.fish
```

::

同样支持 `powershell`，而 `create-nuxt complete <shell>` 有自己的脚本，用于补全起始模板（starter template）名称。

:::note
如果你安装了 [tab 的包管理器补全](https://github.com/bombshell-dev/tab?tab=readme-ov-file#package-manager-completions)，那么通过你的包管理器同样可以使用补全（`pnpm nuxt <Tab>`）。
:::

## 更新通知

CLI 每天会在后台检查一次是否存在更新的 Nuxt 版本，如果存在，就会在命令执行结束后打印一条简短提示，建议你运行 [`nuxt upgrade`](/docs/api/commands/upgrade)。`latest` dist-tag 从你的 `.npmrc` 中配置的 registry 读取，并缓存在你的用户级 `.nuxtrc` 中。

对于预发布版本不会显示这条提示；同一 minor 版本内的补丁更新也不会提示，除非你已经落后至少五个补丁。在 CI 环境中、在 StackBlitz 上，以及输出不是终端时，都会跳过这一检查。

设置 `NUXT_IGNORE_UPDATE_CHECK=1` 或 `NO_UPDATE_NOTIFIER=1` 可以在某一次运行中跳过它；或者在用户级 `.nuxtrc` 中添加 `updateCheck.enabled=false` 以彻底关闭它。

## 网络与代理

需要访问网络的命令（安装模块、搜索模块、下载模板、检查更新）会报告请求失败的原因，而不是抛出原始错误，并给出很可能可行的重试建议。如果你位于一个会对 TLS 流量重新签名的代理之后，这意味着要设置 `NODE_EXTRA_CA_CERTS`，指向你所在组织的根证书。

只有在设置了 `NODE_USE_ENV_PROXY` 时 Node 才会读取代理相关的环境变量，而 CLI 会把这一设置传递给它派生出的进程，因此由 `nuxt add` 发起的包管理器安装看到的代理配置与你的一致。

## 预发布版本

`main` 分支上的每一次提交都会发布到 nightly 通道：

```bash [Terminal]
npm install -D @nuxt/cli-nightly
npx @nuxt/cli-nightly dev
```

`create-nuxt-nightly` 会配合它一起搭建脚手架，而 `npm create nuxt@latest -- --nightly` 则基于 Nuxt nightly 通道搭建项目脚手架。

针对单个 pull request 的构建由 [pkg.pr.new](https://pkg.pr.new) 发布，并在该 pull request 中给出链接，这也是在某项修复正式发布之前验证它是否生效的最快方式。

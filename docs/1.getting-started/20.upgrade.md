## 升级 Nuxt（Upgrading Nuxt）

### 最新版本（Latest release）

要将 Nuxt 升级到 [最新版本](https://github.com/nuxt/nuxt/releases)，请使用 `nuxt upgrade` 命令。

:::code-group{sync="pm"}

```bash [npm]
npx nuxt upgrade
```

```bash [yarn]
yarn nuxt upgrade
```

```bash [pnpm]
pnpm nuxt upgrade
```

```bash [bun]
bun x nuxt upgrade
```

```bash [deno]
deno x nuxt upgrade
```

:::

### 夜间发布通道（Nightly Release Channel）

要在正式发布之前使用最新的 Nuxt 构建和测试特性，请阅读 [夜间发布通道](/docs/guide/going-further/nightly-release-channel) 指南。

## 迁移到 Nuxt 5（Migrating to Nuxt 5）

Nuxt 5 包含大量改进与变更。本指南说明发生了哪些变化，以及如何把现有的 Nuxt 4 应用迁移过来。

首先，按照[上文说明](#upgrading-nuxt)升级 Nuxt。

:::tip
如果你的服务端代码或你所用的模块是为 Nitro v2 编写的（它们从 `h3`、`nitropack` 或 `#imports` 导入，或调用 `useRuntimeConfig(event)`），请先设置 `nitroLegacy: true` 让应用跑起来，然后再逐部分迁移。参阅 [Nitro v2 兼容性](#nitro-v2-compatibility)。
:::

Nuxt 5 的大部分行为已经成为新的默认值。对于仍然可以配置的变化，描述它的章节会指明用于恢复 Nuxt 4 行为的选项；对于无法恢复的，章节中会明确说明。

这些变化包括：

- **Node.js 版本**：Nuxt 5 [要求 Node.js `^22.22.0`、`^24.15.0` 或 `>=26.0.0`](/docs/getting-started/upgrade#nodejs-version-requirements)
- **Nitro v3**：服务端引擎[基于 h3 v2 与 srvx 重写](/docs/getting-started/upgrade#migration-to-nitro-v3)，并为你尚未迁移的服务端代码提供[兼容层](/docs/getting-started/upgrade#nitro-v2-compatibility)
- **服务端导入**：服务端工具函数来自 [`nuxt/server`](/docs/getting-started/upgrade#server-imports-move-to-nuxtserver)，其中包括[会话辅助函数](/docs/getting-started/upgrade#sessions-come-from-nuxtserver)
- **Vite Environment API**：Vite 插件现在[按环境（environment）注册与配置](/docs/getting-started/upgrade#migration-to-vite-environment-api)
- **Vite 8**：打包器[改为 Rolldown，而不再是 esbuild 和 Rollup](/docs/getting-started/upgrade#migration-to-vite-8)
- **Nitro 作为一个 Vite 环境**：使用 `@nuxt/vite-builder` 时，服务端与客户端[由同一次 Vite 构建产出](/docs/getting-started/upgrade#nitro-builds-as-a-vite-environment)
- **Rsbuild 构建工具**：`@nuxt/rspack-builder` 已被弃用，由 [`@nuxt/rsbuild-builder`](/docs/getting-started/upgrade#rspack-builder-is-replaced-by-the-rsbuild-builder) 取代
- **类型化的 `$fetch`**：`$fetch` 和 `useFetch` 的类型来自[生成的路由类型](/docs/getting-started/upgrade#typed-fetch-rebuilt-on-generated-route-types)，而不再是 nitro 的 `InternalApi`
- **客户端不再有 `globalThis.$fetch`**：在浏览器中，`$fetch` [需要通过导入获得，而不再是全局变量](/docs/getting-started/upgrade#fetch-is-no-longer-a-global-in-the-browser)
- **不再打包 `jiti`**：`nuxt.config`、`modules/` 和层配置改为[由运行时直接加载](/docs/getting-started/upgrade#jiti-is-no-longer-bundled)
- **移除 `process.*` 类型扩展**：TypeScript 不再暴露 `NodeJS.Process` 上[已弃用的 `process.*` 标记](/docs/getting-started/upgrade#process-type-augmentation-removed)
- **区分大小写的路由**：页面路由[严格匹配 URL 的大小写](/docs/getting-started/upgrade#case-sensitive-routing)，与 Nitro 保持一致
- **规范化的页面组件名**：页面组件名现在[与其路由名一致](/docs/getting-started/upgrade#normalized-page-component-names)，以保证 `<KeepAlive>` 行为一致
- **可序列化的页面 meta**：可静态分析的 `definePageMeta` 值会被[写入生成的路由记录](/docs/getting-started/upgrade#serializable-page-meta-extracted-at-build-time)
- **客户端 payload 提取**：[`experimental.payloadExtraction`](/docs/getting-started/upgrade#payload-extraction-defaults-to-client) 默认为 `'client'`，会把 payload 内联进预渲染页面的 HTML 中
- **`clearNuxtState` 重置为默认值**：`clearNuxtState` 现在[把状态重置为初始值](/docs/getting-started/upgrade#respect-defaults-when-clearing-usestate)，而不是设为 `undefined`
- **`navigateTo` 提前返回**：顶层的 `await navigateTo()` 成功后[会阻止 `setup()` 中其余代码继续运行](/docs/getting-started/upgrade#early-return-from-navigateto)
- **`navigateTo` 的 `noopener`**：通过 `navigateTo(url, { open })` 打开的窗口[默认带上 `noopener`](/docs/getting-started/upgrade#noopener-for-windows-opened-by-navigateto)，因此它们无法访问 `window.opener`
- **服务端错误边界**：`<NuxtErrorBoundary>` 现在[捕获其默认插槽在服务端渲染期间抛出的错误](/docs/getting-started/upgrade#nuxterrorboundary-catches-server-side-errors)，而不是让错误一路逃逸到错误页
- **非 async 的 `callHook`**：[`callHook` 可以返回 `void`](/docs/getting-started/upgrade#non-async-callhook)，而不再总是返回一个 `Promise`
- **注释节点占位符**：仅客户端组件在 SSR 时使用[注释节点而不是 `<div>` 作为占位](/docs/getting-started/upgrade#client-only-comment-placeholders)，修复了一个 scoped 样式的水合问题
- **服务端自动导入关闭**：服务端代码[显式导入 Nitro 的辅助函数](/docs/getting-started/upgrade#server-auto-imports-are-now-opt-in)，不再依赖自动导入层
- **类型化的 runtime config 环境变量**：环境变量会被[转换为其所替换的 runtime config 值的类型](/docs/getting-started/upgrade#runtime-config-environment-variables-follow-the-type-of-their-value)，并且 runtime config 可以用 schema 来声明
- **仅顶层 `server/utils/`**：位于 [`server/utils/` 子目录](/docs/getting-started/upgrade#nested-serverutils-files-are-no-longer-auto-imported)中的文件不再被自动导入
- **解析后的 `error.data`**：[`experimental.parseErrorData`](/docs/getting-started/upgrade#experimentalparseerrordata-is-no-longer-configurable) 被强制开启，因此 `error.data` 会以未字符串化的形式抵达错误页
- **错误响应格式**：页面错误返回错误页、服务端路由错误返回 JSON，[与请求头无关](/docs/getting-started/upgrade#error-format-depends-on-where-the-error-is-thrown)
- **构建工具的文件监听器**：在开发模式下，Nuxt [复用构建工具自身的监听器](/docs/getting-started/upgrade#builder-file-watcher-in-development)，而不再另起一个
- **仅服务端的 head 组合式函数**：`useServerHead`、`useServerHeadSafe` 和 `useServerSeoMeta` [不再被自动导入](/docs/getting-started/upgrade#server-only-head-composables-are-no-longer-auto-imported)，`unhead.legacy` 也会被忽略
- **禁用 Vue Options API**：[Options API 会从客户端构建中编译移除](/docs/getting-started/upgrade#vue-options-api-disabled-by-default)以减小体积
- **类型化页面**：[`experimental.typedPages`](/docs/getting-started/upgrade#typed-pages-enabled-by-default) 默认开启，提供经过类型检查的路由
- **基于 Node 解析的配置类型**：生成的 `node` tsconfig 会[描述运行时如何加载 `nuxt.config` 和模块](/docs/getting-started/upgrade#jiti-is-no-longer-bundled)
- **更严格的副作用导入**：生成的 `tsconfig.json` 启用了 [`noUncheckedSideEffectImports`](/docs/getting-started/upgrade#stricter-side-effect-imports)，与 TypeScript 7 的默认值保持一致
- **忽略 TypeScript `baseUrl`**：生成的 TypeScript 配置[不再使用 `compilerOptions.baseUrl`](/docs/getting-started/upgrade#typescript-baseurl-is-ignored) 来解析 Nuxt 别名
- **PostCSS 插件**：`autoprefixer` 和 `cssnano` [不再默认安装或配置](/docs/getting-started/upgrade#postcss-plugins-are-no-longer-installed-by-default)
- **可选依赖**：[`@vitejs/plugin-vue-jsx`](/docs/getting-started/upgrade#vitejsplugin-vue-jsx-is-now-optional) 和 [`giget`](/docs/getting-started/upgrade#giget-is-now-optional-remote-layers) 按需安装
- **对等依赖**：[`vue` 和 `vue-router`](/docs/getting-started/upgrade#vue-and-vue-router-are-peer-dependencies) 来自你的项目，并且只有在启用 pages 时才需要 `vue-router`
- **代理环境变量**：构建时的请求[使用 Node 内置的代理支持](/docs/getting-started/upgrade#build-time-proxy-support-uses-nodejs)，不再使用 `undici`；在 Node.js 22 上需要设置 `NODE_USE_ENV_PROXY=1`
- **移除的选项**：[若干实验性选项](/docs/getting-started/upgrade#removed-configuration-options)已被删除，因为它们所控制的行为现在是无条件生效的

:::note
Nuxt 5 仍在开发中，因此随着后续工作落地，本页会持续变化。在迁移期间请经常回来查看。
:::

下面列出的是破坏性或重大的变更，并附有迁移步骤以及每一项可用的配置。

### Node.js 版本要求（Node.js Version Requirements）

🚦 **影响级别**：最小

#### 发生了什么变化（What Changed）

Nuxt 5 支持 Node.js `^22.22.0`、`^24.15.0` 和 `>=26.0.0`。在 Node.js 24 上，最低版本现在是 24.15.0，与当前的 Nuxt 4 发布版保持一致。

#### 迁移步骤（Migration Steps）

如果你使用的是 Node.js 24.11 到 24.14，请升级到最新的 Node.js 24 版本。

### 移除 `process.*` 类型扩展（`process.*` Type Augmentation Removed）

🚦 **影响级别**：最小

#### 发生了什么变化（What Changed）

Nuxt 不再为 `NodeJS.Process` 扩展 `browser`、`client`、`dev`、`server` 和 `test`。为保证兼容性，构建时 defines 中这些标记仍然存在，但 TypeScript 不会再把它们当作已知属性。

请优先使用 [`import.meta.*`](/docs/api/advanced/import-meta)。这些标记在构建时被替换，并且可以保持 tree-shakeable。

#### 迁移步骤（Migration Steps）

在你的应用代码、模块和库中替换旧写法：

```ts
// 之前
// eslint-disable-next-line nuxt/prefer-import-meta
if (process.server) {
  /* ... */
}

// 之后
if (import.meta.server) {
  /* ... */
}
```

[`nuxt/prefer-import-meta`](https://eslint.nuxt.com/packages/plugin#nuxtprefer-import-meta) ESLint 规则会标出仍然存在的 `process.*` 用法。

### 区分大小写的路由（Case-Sensitive Routing）

🚦 **影响级别**：最小

#### 发生了什么变化（What Changed）

`router.options.sensitive` 现在默认为 `true`，因此页面路由会以区分大小写的方式匹配 URL，与 Nitro 保持一致。例如，`/About` 不再匹配 `pages/about.vue`。

`sensitive` 现在只从 `nuxt.config` 读取，因为服务端会用同一设置来匹配路由规则。如果 `app/router.options.ts` 设置了它，构建将失败。

#### 迁移步骤（Migration Steps）

更新链接，使其大小写与页面路由一致。若要保留不区分大小写的匹配，请在 `nuxt.config` 中设置 `sensitive`（如果 `app/router.options.ts` 中有该设置，请移除它）：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  router: {
    options: {
      sensitive: false,
    },
  },
})
```

如果你选择关闭，路由规则中的正则约束必须按[小写字母](/docs/guide/recipes/custom-routing#route-rules-with-case-insensitive-routing)来编写。

### 规范化的页面组件名（Normalized Page Component Names）

🚦 **影响级别**：最小

#### 发生了什么变化（What Changed）

`experimental.normalizePageNames` 现在默认启用，因此页面组件按路由而非文件名命名。`pages/foo/index.vue` 和 `pages/bar/index.vue` 的名字分别是 `foo` 和 `bar`，而不是都叫 `index`。

#### 迁移步骤（Migration Steps）

如果你按组件名过滤 `<KeepAlive>`，请把 `include`/`exclude` 更新为路由名。若要保留基于文件名的命名：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    normalizePageNames: false,
  },
})
```

### 构建时提取可序列化的页面 Meta（Serializable Page Meta Extracted at Build Time）

🚦 **影响级别**：最小

#### 发生了什么变化（What Changed）

`experimental.extractSerializablePageMeta` 现在默认启用。每个可 JSON 序列化的 `definePageMeta()` 属性都会被写入生成的路由记录，而不再只写入一份固定键列表（外加 `experimental.extraPageMetaExtractionKeys`）、其余部分在运行时从每页的 meta 模块解析。

对于值无法序列化的属性，例如函数、变量引用和展开语法，仍然会在运行时解析。

#### 迁移步骤（Migration Steps）

如果你（例如在 `pages:extend` 钩子中）在构建时从路由记录读取页面 meta，那么现在应该能直接看到被提取出来的值。若要保留之前的行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    extractSerializablePageMeta: false,
  },
})
```

### Payload 提取默认值为 `'client'`（Payload Extraction Defaults to `'client'`）

🚦 **影响级别**：最小

#### 发生了什么变化（What Changed）

`experimental.payloadExtraction` 现在的默认值是 `'client'`，而不是 `true`。预渲染或被缓存页面的 payload 会内联在首次渲染的 HTML 中，而 `_payload.json` 文件只在客户端导航时才抓取。当禁用 `ssr` 时，它仍会被强制设为 `false`。

#### 迁移步骤（Migration Steps）

大多数应用无需任何改动。如果你自己为首次渲染抓取 `_payload.json`，或在测试中测量 HTML 体积，请显式设置该选项：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    payloadExtraction: true,
  },
})
```

:::read-more{to="/docs/getting-started/prerendering#payload-extraction"}
阅读更多关于 payload 提取以及每种模式带来的影响。
:::

### 清除 `useState` 时保留默认值（Respect Defaults When Clearing `useState`）

🚦 **影响级别**：最小

#### 发生了什么变化（What Changed）

`experimental.defaults.useState.resetOnClear` 现在默认启用，因此 [`clearNuxtState`](/docs/api/utils/clear-nuxt-state) 会把状态重置为 [`useState`](/docs/api/composables/use-state) 的 `init` 函数所产生的值，而不是把它设为 `undefined`。

#### 迁移步骤（Migration Steps）

如果你的代码在清除状态后检查 `undefined`，请改为检查初始值。若要保留之前的行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    defaults: {
      useState: {
        resetOnClear: false,
      },
    },
  },
})
```

### `navigateTo` 提前返回（Early Return From `navigateTo`）

🚦 **影响级别**：最小

#### 发生了什么变化（What Changed）

`experimental.navigateToEarlyReturn` 现在默认启用。在 `<script setup>` 中顶层的 `await navigateTo()` 会在导航成功时被编译成从 `setup()` 提前返回，因此其余的 setup 代码不会运行，组件在导航进行期间只渲染一个占位注释。

#### 迁移步骤（Migration Steps）

如果你依赖「`await navigateTo()` 成功之后的代码仍然运行」，请把这些代码移到导航之前。若要保留之前的行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    navigateToEarlyReturn: false,
  },
})
```

### `navigateTo` 打开的窗口默认使用 `noopener`（`noopener` for Windows Opened by `navigateTo`）

🚦 **影响级别**：最小

#### 发生了什么变化（What Changed）

`experimental.defaults.navigateTo.noopener` 现在默认启用，因此带 `open` 选项的 [`navigateTo`](/docs/api/utils/navigate-to) 会向 `window.open` 传入 `noopener`，除非设置了 `open.windowFeatures.noopener`。被打开的页面不再能通过 `window.opener` 访问你的应用；并且使用具名 `target`（除 `_self`、`_parent`、`_top` 之外）时，每次都会打开新窗口，而不是复用同名的已有窗口。

#### 迁移步骤（Migration Steps）

如果被打开的页面依赖 `window.opener`（例如调用 `window.opener.postMessage()` 的 OAuth 弹窗），或者你在复用具名窗口，请为该次调用设置 `noopener: false`：

```ts
await navigateTo('https://auth.example.com/authorize', {
  external: true,
  open: { windowFeatures: { popup: true, noopener: false } },
})
```

要在所有位置保留之前的行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    defaults: {
      navigateTo: {
        noopener: false,
      },
    },
  },
})
```

### `<NuxtErrorBoundary>` 捕获服务端错误（`<NuxtErrorBoundary>` Catches Server-Side Errors）

🚦 **影响级别**：中等

#### 发生了什么变化（What Changed）

`experimental.ssrErrorBoundary` 现在默认启用。当 [`<NuxtErrorBoundary>`](/docs/api/components/nuxt-error-boundary) 内部的内容在服务端渲染期间抛出错误时，边界会在 HTML 响应中渲染它的 `#error` 插槽，并使用 `200` 状态码，客户端随后水合到相同的状态。之前的行为是错误逃逸到全屏错误页，并带上错误的状态码。

这包括在页面 `setup` 中使用 `createError({ status: 404 })` 创建的错误：如果 `<NuxtPage>` 或布局中的 `<slot />` 被包在边界内，这样的页面现在会响应 `200` 以及边界的 `#error` 插槽。

`<NuxtClientFallback>` 和 `experimental.clientFallback` 已被弃用，请改用 `<NuxtErrorBoundary retry-on-client>`。

#### 迁移步骤（Migration Steps）

如果某个页面依赖抛出错误来返回错误页及其状态码，请调整边界位置使它不再包裹该页面，或者改为调用 [`showError`](/docs/api/utils/show-error) 而不是抛出错误。若要保留之前的行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    ssrErrorBoundary: false,
  },
})
```

### 开发模式下使用构建工具的文件监听器（Builder File Watcher in Development）

🚦 **影响级别**：最小

#### 发生了什么变化（What Changed）

`experimental.watcher` 现在默认为 `'builder'`，因此 Nuxt 会复用当前构建工具的文件监听器（例如 Vite 的 `server.watcher`），而不是另起一个。如果构建工具没有提供监听器，Nuxt 会回退到之前的选择。

#### 迁移步骤（Migration Steps）

如果你依赖监听那些被构建工具忽略的文件，请显式指定一个监听器：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    watcher: 'chokidar',
  },
})
```

### 不再打包 `jiti`（`jiti` Is No Longer Bundled）

🚦 **影响级别**：中等

#### 发生了什么变化（What Changed）

Nuxt 不再依赖 [`jiti`](https://github.com/unjs/jiti)。在打包器之外加载的文件（`nuxt.config.ts`、`modules/` 中的文件以及层配置）现在由运行时自身导入。

**你仍然可以用 TypeScript 编写配置。** Nuxt 5 要求 Node `22.22`、`24.15` 或更高版本，这些版本默认开启类型剥离（type stripping），因此 `nuxt.config.ts` 和 TypeScript 模块可以原生加载。运行时不会做、而过去由 `jiti` 掩盖掉的两件事是：猜测文件扩展名，以及编译会产出代码的 TypeScript 语法。

这两类问题本来只会在 Nuxt 加载文件时才暴露，因此生成的 `node` tsconfig 现在按运行时实际的看法来描述该环境（`module` 和 `moduleResolution` 设为 `nodenext`，并加上 [`erasableSyntaxOnly`](https://www.typescriptlang.org/tsconfig/#erasableSyntaxOnly)），TypeScript 会提前报告这两类问题。

这只影响 `nuxt.config`、`modules/` 和层配置。你的应用代码和 `shared/` 代码仍然经过 Vite，解析方式一如既往。如果你需要之前的行为，可以覆盖它：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  typescript: {
    nodeTsConfig: {
      compilerOptions: {
        module: 'preserve',
        moduleResolution: 'bundler',
        erasableSyntaxOnly: false,
      },
    },
  },
})
```

#### 变更原因（Reasons for Change）

过去每次安装 Nuxt 都要拉入 `jiti`，只为加载少量文件，而其中大部分文件运行时现在已能自行加载。移除它可以让默认安装体积更小。

#### 迁移步骤（Migration Steps）

**1. 为相对导入补上文件扩展名。**

`nuxt.config.ts`、`modules/` 和层配置中的相对导入需要显式扩展名：

```diff [nuxt.config.ts]
- import { myPlugin } from './build/my-plugin'
+ import { myPlugin } from './build/my-plugin.ts'
```

TypeScript 会用 `TS2835` 报告缺失的扩展名。注意它的快速修复建议写成 `./build/my-plugin.js`；请写文件实际的扩展名（`.ts`），Node 可以直接解析它。

裸包导入（`import { defu } from 'defu'`）不受影响。

JSON 导入需要一个导入属性（import attribute）：

```diff [modules/my-module.ts]
- import pkg from '../package.json'
+ import pkg from '../package.json' with { type: 'json' }
```

`~/`、`#shared` 这类 Nuxt 别名在打包器之外不会被解析，因此请改用相对导入：

```diff [modules/my-module.ts]
- import { CONSTANTS } from '#shared/utils/constants'
+ import { CONSTANTS } from '../shared/utils/constants.ts'
```

**2. 使用可擦除的 TypeScript 语法。**

类型标注会被擦除，但会产出运行时代码的语法不行。在配置文件和模块文件中，请替换：

- 把 `enum Foo {}` 换成 `const` 对象
- 把 `namespace` / `module` 块换成普通导出
- 把构造函数参数属性（`constructor(private x: string) {}`）换成显式赋值
- 实验性装饰器

TypeScript 会以 `TS1294` 为你报告以上所有情况。

**3. 如果你发布层或模块，请随包发布编译后的 JavaScript。**

这一点专门针对第三方包。无论配置如何，运行时都拒绝为 `node_modules` 内的任何文件剥离类型，因此用 TypeScript 编写的已发布入口点，无论 Node 版本多新都无法原生加载。请在发布前构建为 JavaScript；如果你的包带有 `nuxt.config`，请把它输出为 `nuxt.config.mjs`。否则每个使用该包的项目都得安装 `jiti`。

这不适用于你自己项目内的层：`layers/*/nuxt.config.ts` 可以原生加载。

**4. 如果仍然需要 `jiti`，请自行安装。**

`jiti` 现在是一个可选的对等依赖。安装它之后，每当运行时无法自行加载某个文件时，Nuxt 都会自动把它作为回退方案拾取：

:::code-group{sync="pm"}

```bash [npm]
npm i -D jiti
```

```bash [yarn]
yarn add -D jiti
```

```bash [pnpm]
pnpm add -D jiti
```

```bash [bun]
bun add -D jiti
```

:::

`nuxt.schema` 文件也以同样方式由运行时导入，并且 Nuxt 会在导入它们时读取其中的 JSDoc 注解。因此它们遵循与配置文件相同的规则：位于 `node_modules` 中的 `nuxt.schema.ts`（例如已发布层自带的）会通过 `jiti` 加载。在没有 `module.registerHooks()` 的运行时（例如 Bun）上，所有 `nuxt.schema` 文件都通过 `jiti` 加载。

随之而来的还有一个较小的变化：`postcss.plugins` 中列出的 PostCSS 插件现在由运行时解析，因此只能通过 Nuxt `alias` 条目解析的插件名将不再能加载。请使用包名或路径。

### 迁移到 Vite Environment API（Migration to Vite Environment API）

🚦 **影响级别**：中等

#### 发生了什么变化（What Changed）

Nuxt 5 迁移到 Vite 6 全新的 [Environment API](https://vite.dev/guide/api-environment)，它正式化了「环境」这一概念，并让你能更好地按环境控制配置。

以前，Nuxt 使用相互分离的 client 和 server Vite 配置。现在，Nuxt 使用一份共享的 Vite 配置，配合使用 `applyToEnvironment()` 方法定位特定环境的环境专属插件。

:::note
Vite Environment API 在 Nuxt 5 中始终启用。`experimental.viteEnvironmentApi` 选项已被移除。
:::

**关键变更：**

1. **弃用环境专属的 `extendViteConfig()`**：`extendViteConfig()` 中的 `server` 和 `client` 选项已被弃用，使用时会出现警告。

2. **插件注册方式变化**：通过 `addVitePlugin()` 注册且只作用于单个环境（传入 `server: false` 或 `client: false`）的 Vite 插件，其 `config` 或 `configResolved` 钩子不会被调用。

3. **共享配置**：`vite:extendConfig` 和 `vite:configResolved` 钩子现在作用于共享配置，而不再是分开的 client/server 配置。

#### 变更原因（Reasons for Change）

Vite Environment API 带来了：
- 开发模式与生产构建之间更好的一致性
- 对环境专属配置更细粒度的控制
- 改进的性能与插件架构
- 支持 client 和 server 之外的自定义环境

#### 迁移步骤（Migration Steps）

##### 1. 改为使用 Vite 插件

我们建议你使用 Vite 插件，而不是 `extendViteConfig`、`vite:configResolved` 和 `vite:extendConfig`。

```ts
// 之前
extendViteConfig((config) => {
  config.optimizeDeps.include.push('my-package')
}, { server: false })

nuxt.hook('vite:extendConfig' /* 或 vite:configResolved */, (config, { isClient }) => {
  if (isClient) {
    config.optimizeDeps.include.push('my-package')
  }
})

// 之后
addVitePlugin(() => ({
  name: 'my-plugin',
  config (config) {
    // 你可以在这里设置全局 vite 配置
  },
  configResolved (config) {
    // 你可以在这里访问完全解析后的 vite 配置
  },
  configEnvironment (name, config) {
    // 你可以在这里设置环境专属的 vite 配置
    if (name === 'client') {
      config.optimizeDeps ||= {}
      config.optimizeDeps.include ||= []
      config.optimizeDeps.include.push('my-package')
    }
  },
  applyToEnvironment (environment) {
    return environment.name === 'client'
  },
}))
```

##### 2. 迁移 Vite 插件以使用环境

与其在 `addVitePlugin` 上传入 `server: false` 或 `client: false`，你可以在插件内部使用新的 `applyToEnvironment` 钩子。

```ts
// 之前
addVitePlugin(() => ({
  name: 'my-plugin',
  config (config) {
    config.optimizeDeps.include.push('my-package')
  },
}), { client: false })

// 之后
addVitePlugin(() => ({
  name: 'my-plugin',
  config (config) {
    // 你可以在这里设置全局 vite 配置
  },
  configResolved (config) {
    // 你可以在这里访问完全解析后的 vite 配置
  },
  configEnvironment (name, config) {
    // 你可以在这里设置环境专属的 vite 配置
    if (name === 'client') {
      config.optimizeDeps ||= {}
      config.optimizeDeps.include ||= []
      config.optimizeDeps.include.push('my-package')
    }
  },
  applyToEnvironment (environment) {
    return environment.name === 'client'
  },
}))
```

:::read-more{to="https://vite.dev/guide/api-environment" target="_blank"}
了解更多关于 Vite Environment API 的内容
:::

### 迁移到 Vite 8（Migration to Vite 8）

🚦 **影响级别**：中等

#### 发生了什么变化（What Changed）

Nuxt 5 从 Vite 7 升级到 [Vite 8](https://main.vite.dev/guide/migration)，后者用 [Rolldown](https://rolldown.rs) 取代了 esbuild 和 Rollup 作为底层打包器。这带来了显著更快的构建，但也包含若干破坏性变更。

:::note
这里没有开关：Nuxt 5 要求使用 Vite 8。如果你想先在 Nuxt 4 上测试 Vite 8 兼容性，可以在 `package.json` 中添加 `"vite": "^8.3.0"` 解析覆盖。
:::

大部分迁移由 Nuxt 内部处理，但有一些面向用户的变更需要留意：

- **`vite.esbuild` 和 `vite.optimizeDeps.esbuildOptions`** 已被弃用，请改用 `vite.oxc` 和 `vite.optimizeDeps.rolldownOptions`。目前 Vite 8 会自动转换它们，但它们将来会被移除。
- **`build.rollupOptions`** 已被弃用，请改用 `build.rolldownOptions`。
- **CommonJS 互操作行为**发生了变化。如果你导入 CJS 模块，请查阅 [Vite 8 迁移指南](https://main.vite.dev/guide/migration#consistent-commonjs-interop)了解详情。

:::read-more{to="https://main.vite.dev/guide/migration" target="_blank"}
查看完整的 Vite 8 迁移指南，了解所有破坏性变更与迁移步骤。
:::

### Nitro 作为一个 Vite 环境构建（Nitro Builds as a Vite Environment）

🚦 **影响级别**：中等

#### 发生了什么变化（What Changed）

在使用 `@nuxt/vite-builder` 时，`experimental.nitroViteEnvironment` 现在默认为 `true`，因此 Nitro 会通过 `nitro/vite` 插件作为一个 [Vite 环境](https://vite.dev/guide/api-environment) 构建，而不是走 Nitro 自己的 Rolldown 流程。服务端与客户端由同一次 Vite 构建产出，服务端代码也会经过你的应用代码已经在使用的 Vite 插件与解析逻辑。

对于其他应用构建工具，该选项没有效果，它们仍使用 Nitro 自己的流程。在那里把它设为 `true` 会记录一条警告。

#### 迁移步骤（Migration Steps）

`nitro.rollupConfig.plugins` 中的插件仍然在 `nitro` 环境中运行，但会在 Vite 自身的解析与核心转换之后。如果一个插件必须在 Vite 之前解析或转换某个模块，它需要成为一个带 `enforce: 'pre'` 的 Vite 插件。

`addVitePlugin()` 只为应用的各个环境注册插件，因此若要为服务端构建添加插件，请直接写入 `vite.plugins`，并用 `applyToEnvironment` 限定作用范围：

```ts [module.ts]
import { defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule({
  setup (_options, nuxt) {
    nuxt.options.vite.plugins ||= []
    nuxt.options.vite.plugins.push({
      name: 'my-module:server',
      enforce: 'pre',
      applyToEnvironment: environment => environment.name === 'nitro',
      resolveId (id) {
        // ...
      },
    })
  },
})
```

要保留 Nitro 自己的构建流程：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    nitroViteEnvironment: false,
  },
})
```

### Rspack 构建工具被 Rsbuild 构建工具取代（Rspack Builder Is Replaced by the Rsbuild Builder）

🚦 **影响级别**：中等（仅当你使用 `builder: 'rspack'` 时）

#### 发生了什么变化（What Changed）

Nuxt 新增了一个构建工具 `@nuxt/rsbuild-builder`，通过 `builder: 'rsbuild'` 启用。它使用 [Rsbuild](https://rsbuild.rs)（运行在 Rspack 之上）来构建你的应用，并通过新的 [`rsbuild`](/docs/api/nuxt-config#rsbuild) 选项进行配置。

`@nuxt/rspack-builder` 已被弃用并会记录警告。它在 Nuxt 5 中仍然可用，并将在未来的某个主版本中被移除。

#### 变更原因（Reasons for Change）

`@nuxt/rspack-builder` 是基于 webpack 构建工具的预设来生成其 Rspack 配置的，并配有处理 CSS、PostCSS、esbuild 和资源文件的 loader。`@nuxt/rsbuild-builder` 则改用 Rsbuild 自身对这些内容的处理方式（脚本用 SWC，样式用 Lightning CSS），并配合 Rsbuild 插件生态。

#### 迁移步骤（Migration Steps）

用 `@nuxt/rsbuild-builder` 替换 `@nuxt/rspack-builder`：

:::code-group{sync="pm"}

```bash [npm]
npm uninstall @nuxt/rspack-builder
npm install -D @nuxt/rsbuild-builder
```

```bash [yarn]
yarn remove @nuxt/rspack-builder
yarn add -D @nuxt/rsbuild-builder
```

```bash [pnpm]
pnpm remove @nuxt/rspack-builder
pnpm add -D @nuxt/rsbuild-builder
```

```bash [bun]
bun remove @nuxt/rspack-builder
bun add -D @nuxt/rsbuild-builder
```

:::

然后更新你 `nuxt.config` 中的 builder：

```diff
  export default defineNuxtConfig({
-   builder: 'rspack',
+   builder: 'rsbuild',
  })
```

Rsbuild 构建工具不会读取 `webpack` 选项，因此请把设置过的选项迁移到 `rsbuild` 选项中。例如 `webpack.loaders.vue` 变为 `rsbuild.vue.vueLoaderOptions`，只作用于某一次构建的选项则放到 `rsbuild.environments.client` 或 `rsbuild.environments.ssr` 下。PostCSS 插件仍然通过 `postcss.plugins` 配置，而 `build.analyze` 会生成一份 [Rsdoctor](https://rsdoctor.rs) 报告。

对你使用的每种语言，请安装对应的 Rsbuild 插件而不是它的 webpack loader。当这些插件已安装时 Nuxt 会自动注册它们，而某个文件需要某个插件却未安装时 Nuxt 会发出警告。

| 语言  | webpack loader     | Rsbuild 插件              |
| --------- | ------------------ | ------------------------ |
| Sass/SCSS | `sass-loader`      | `@rsbuild/plugin-sass`   |
| Less      | `less-loader`      | `@rsbuild/plugin-less`   |
| Stylus    | `stylus-loader`    | `@rsbuild/plugin-stylus` |
| Pug       | `pug-plain-loader` | `@rsbuild/plugin-pug`    |

使用 `typescript.typeCheck` 的类型检查依赖 `@rsbuild/plugin-type-check`，缺失时 Nuxt 会提示你安装它。

#### 面向模块作者（For Module Authors）

- `addRspackPlugin()`、`extendRspackConfig()` 以及带 `rspack` 插件的 `addBuildPlugin()` 仍然有效，`rspack:config` 和 `rspack:configResolved` 钩子也仍会被调用。Rspack 配置现在由 Rsbuild 生成，因此它们的 `module.rules` 与 `@nuxt/rspack-builder` 生成的不同。要改变文件的处理方式，请使用 [`extendRsbuildConfig()`](/docs/api/kit/builder#extendrsbuildconfig) 或 [`addRsbuildPlugin()`](/docs/api/kit/builder#addrsbuildplugin)。
- 服务端构建的名称现在是 `ssr` 而不是 `server`。在 `rspack:config` 中查找服务端配置的代码需要同时检查两者：

  ```diff
    nuxt.hook('rspack:config', (configs) => {
  -   const server = configs.find(config => config.name === 'server')
  +   const server = configs.find(config => config.name === 'server' || config.name === 'ssr')
    })
  ```

- `rspack:compile` 和 `rspack:compiled` 钩子不再被调用。请改用 `rsbuild:compile` 和 `rsbuild:compiled`，它们会接收环境 `name`、对应的 Rspack `compiler`，以及编译完成后的 `stats`。

### 服务端导入迁移到 `nuxt/server`（Server Imports Move to `nuxt/server`）

🚦 **影响级别**：中等

#### 发生了什么变化（What Changed）

Nuxt 5 提供了 `nuxt/server`，它是服务端代码最常用到的那些服务端工具函数的导入入口：`defineHandler`、`createError`、`getQuery`、`readBody`、cookie 与 header 辅助函数、`sendRedirect`、`getRouteRules` 以及 `useRuntimeConfig`。

在 Nuxt 4 中，服务端代码要么从 `h3` 导入这些工具，要么通过自动导入获得，这会把它们绑定到 h3 v1 和 `nitropack`。改为从 `nuxt/server` 导入后，无论配置了哪个 [`server.builder`](/docs/guide/going-further/builders) 都能工作，因此同一个文件可以同时服务 Nuxt 4.6（运行 `nitropack` v2 或 Nitro v3）和 Nuxt 5。

```diff [server/api/hello.ts]
- import { defineEventHandler, getQuery } from 'h3'
+ import { defineHandler, getQuery } from 'nuxt/server'

- export default defineEventHandler((event) => {
+ export default defineHandler((event) => {
    return getQuery(event)
  })
```

`nuxt/server` 也导出 `defineEventHandler` 作为 `defineHandler` 的别名，因此是否重命名你的处理函数是可选的。

错误采用与你应用中 Vue 部分所构造的错误相同的形态：

```diff
- import { createError } from 'h3'
+ import { createError } from 'nuxt/server'

  export default defineHandler(() => {
-   throw createError({ statusCode: 400, statusMessage: 'Bad request' })
+   throw createError({ status: 400, statusText: 'Bad request' })
  })
```

服务端自动导入[在 Nuxt 5 中默认关闭](#server-auto-imports-are-now-opt-in)。通过 `experimental.nitroAutoImports` 启用它的项目会经由自动导入拿到 `nuxt/server`，因此无需更改导入。

#### 迁移步骤（Migration Steps）

1. 把 `h3` 导入替换为 `nuxt/server`，适用于[该导入入口](/docs/guide/going-further/server-imports#types-and-utilities)中列出的工具函数。
2. 其他任何内容请从 `nitro/h3` 导入。`nuxt/server` 并不是 h3 的重新导出，因此像 `proxyRequest` 这样的辅助函数不在其中。
3. 更新受[与 h3 v1 的差异](#differences-from-h3-v1)影响的调用，无论这些辅助函数是显式导入还是自动导入的。

#### 与 h3 v1 的差异（Differences From h3 v1）

| h3 v1 | `nuxt/server` |
|---|---|
| `sendRedirect(event, location)` 会直接发送响应。 | 返回响应体：`return sendRedirect(event, '/login')`。 |
| `getRouterParam(event, name)` 和 `getRouterParams(event)` 返回解码后的值。 | 它们返回 URL 中原样的值。传入 `{ decode: true }` 可解码。 |
| `handleCors(event, options)` 在响应了预检请求时返回 `true`。 | 返回预检的 `Response` 或 `false`：`const preflight = handleCors(event, options); if (preflight) return preflight`。 |
| `handleCors` 在运行时接受单个 origin 字符串。 | `origin` 是 `'*'`、`'null'`、一个 origin 或模式数组，或一个函数：单个 origin 请包在数组里。`maxAge` 是以秒为单位的字符串，例如 `'86400'`，或 `false`。`CorsOptions` 类型请从 `nuxt/server` 导入。 |
| `readValidatedBody` 和 `getValidatedQuery` 接受一个校验函数。 | 它们接受一个 [Standard Schema](https://standardschema.dev) 或一个函数。 |
| `createError({ statusCode, statusMessage })` | `createError({ status, statusText })` |
| `isError(error)` | `isNuxtError(error)` |
| h3 的 `useSession`、`getSession`、`updateSession` 和 `clearSession` 用你传入的 `password` 对一个 `h3` cookie 进行封装（seal）。 | 它们对 `nuxt-session` cookie 进行封装，默认使用从 `appSecret` 派生的密钥。一方签发的会话无法用另一方解封，因此用户会有一次失去原有会话。参阅[会话来自 `nuxt/server`](#sessions-come-from-nuxtserver)。 |
| `useRuntimeConfig(event)` | `useRuntimeConfig()`。没有按请求的形式。 |
| 全局 `$fetch` | 不属于 `nuxt/server`。请用 `serverFetch(event, path)` 调用应用的一个路由，它返回一个 `Response`。对于其他 URL，普通 `fetch` 不会在非 2xx 状态码时抛出错误，也不会解析 JSON：请检查 `response.ok` 并调用 `response.json()`。 |
| `event.path` | `getRequestURL(event).pathname`，或 `event.url.pathname`。 |
| `event.node` | 不可用。请使用 `event.req` 和 `event.res`。 |
| `getResponseHeader`、`setResponseHeader`、`appendResponseHeader`、`removeResponseHeader` | `event.res.headers.get()`、`.set()`、`.append()`、`.delete()` |
| `getMethod(event)`、`isMethod(event, method)`、`assertMethod(event, method)` | 比较 `event.req.method`。 |
| `readMultipartFormData(event)` | `await event.req.formData()` |
| `readRawBody(event)`、`getRequestWebStream(event)` | `await event.req.arrayBuffer()`（或 `.text()`）、`event.req.body` |
| `toWebRequest(event)` | `event.req`，它本身已经是一个 `Request` |
| `sanitizeStatusCode` | 不再提供。 |

:::read-more{to="/docs/guide/going-further/server-imports"}
了解该导入入口涵盖哪些内容，以及它对模块作者意味着什么。
:::

### 会话来自 `nuxt/server`（Sessions Come From `nuxt/server`）

🚦 **影响级别**：中等

#### 发生了什么变化（What Changed）

`useSession`、`getSession`、`updateSession` 和 `clearSession` 现在是 [`nuxt/server`](/docs/guide/going-further/server-imports#sessions) 的一部分，并且自动导入的这些名称解析到的就是它们。它们基于 Web 标准的 `Request` 和 `Response`，使用 `iron-webcrypto` 来封装会话，因此可以在任何 [`server.builder`](/docs/guide/going-further/builders) 下运行，而不只在 Nitro 下。

由 h3 辅助函数签发的会话无法用它们解封，并且默认 cookie 名是 `nuxt-session` 而不是 `h3`。升级之前登录的所有用户会有一次得到全新的空会话。

不再必须提供 `password`。没有它时，会话使用从 [`appSecret`](/docs/guide/going-further/runtime-config#application-secret) 派生的密钥封装，该值由 `NUXT_APP_SECRET` 设置：

```diff [server/api/me.ts]
  export default defineEventHandler(async (event) => {
-   const session = await useSession<{ user?: string }>(event, {
-     password: process.env.NUXT_SESSION_PASSWORD!,
-   })
+   const session = await useSession<{ user?: string }>(event)
    return { user: session.data.user }
  })
```

如果仍传入一个至少 32 个字符的 `password`，则会使用该值来封装。

要保留 h3 的实现，请显式导入它：

```diff [server/api/me.ts]
+ import { useSession } from 'nitro/h3'

  export default defineEventHandler(async (event) => {
    const session = await useSession(event, { password: process.env.NUXT_SESSION_PASSWORD! })
    return { user: session.data.user }
  })
```

#### 迁移步骤（Migration Steps）

1. 预期现有会话会失效：用户会在完成升级的那次部署上被登出一次。
2. 如果你依赖 h3 特有的选项（`sessionHeader`、`crypto`、`seal`），请要么从 `nitro/h3` 导入 `useSession`，要么改用 `nuxt/server` 中的等价项：`name`、`maxAge` 和 `cookie`。
3. 如果你去掉 `password`，请在每个部署环境中设置 `NUXT_APP_SECRET`；在开发模式下 Nuxt 会自动生成一个。
4. 只有当你同时保留 h3 的辅助函数时，才把 cookie 名设为 `h3`；这两种实现不应共用同一个 cookie。

:::read-more{to="/docs/guide/going-further/server-imports#sessions"}
了解会话辅助函数涵盖哪些内容。
:::

### Runtime Config 环境变量跟随其值的类型（Runtime Config Environment Variables Follow the Type of Their Value）

🚦 **影响级别**：中等

#### 发生了什么变化（What Changed）

覆盖某个 [runtime config](/docs/guide/going-further/runtime-config#environment-variables) 值的环境变量，现在会被转换为 `nuxt.config` 中该值的类型，而不再用 `destr` 根据内容猜测类型。当 `port` 的默认值是 `3000` 时，`NUXT_PORT=8080` 是一个数字；当 `apiSecret` 的默认值是 `''` 时，`NUXT_API_SECRET=4848e0` 保持为字符串。

如果某个变量无法转换（例如 `NUXT_PORT=abc`），服务端将不会启动，并报告 [`NUXT_E8014`](/docs/errors/e8014)。

runtime config 的值还可以[用 Standard Schema 声明](/docs/guide/going-further/runtime-config#validating-with-a-schema)，例如 Zod 或 ArkType 的 schema，从而在不提供默认值的情况下确定其类型，或将其声明为必填。

#### 迁移步骤（Migration Steps）

1. 移除那些仅仅为了让值保持字符串而加上的字面双引号，例如 `NUXT_MY_VAR='"4848e0"'`。在有字符串默认值的情况下，这些引号现在会成为值的一部分。
1. 确保每个默认值的类型就是你要读取的类型。一个默认值为 `''` 却被设置为 `NUXT_RETRIES=3` 的值，现在是字符串 `'3'`。请为它提供数字类型的默认值，或提供一个 schema：

```ts [nuxt.config.ts]
import { z } from 'zod'

export default defineNuxtConfig({
  runtimeConfig: {
    retries: 3,
    apiSecret: z.string(),
  },
})
```

对于默认值为 `null` 或 `undefined` 的普通值，它们会被替换为空字符串，因此也会被当作字符串设置。像 `z.number().nullable().default(null)` 这样的 schema 会保留它的 `null` 默认值。

### 迁移到 Nitro v3（Migration to Nitro v3）

🚦 **影响级别**：重大

#### 发生了什么变化（What Changed）

Nuxt 5 升级到 [Nitro v3](https://nitro.build/blog/v3-beta)，这是服务端引擎的一次重大重写。Nitro v3 构建于 [srvx](https://srvx.h3.dev) 和 [h3 v2](https://h3.dev) 之上，全面采用 Web 标准的 `Request`/`Response` API。这带来了性能改进和更一致的 API，但也包含对服务端代码的若干破坏性变更。

:::important
我们仍在处理 Nitro v3 的集成，因此你应该预期还会有进一步的变更，以及为让迁移更顺畅而需要额外完成的工作。
:::

:::read-more{to="https://nitro.build/blog/v3-beta" target="_blank"}
阅读 Nitro v3 beta 公告以了解全貌。
:::

:::read-more{to="https://nitro.build/docs/migration" target="_blank"}
查看完整的 Nitro v3 迁移指南，了解所有破坏性变更。
:::

下面各小节重点介绍与 Nuxt 应用开发者和模块作者最相关的变更。你不必在升级之前完成其中全部改动：参阅 [Nitro v2 兼容性](#nitro-v2-compatibility)，了解在此期间让旧服务端代码继续运行的兼容层。

#### 包与导入路径变更（Package and Import Path Changes）

`nitropack` 包已重命名为 `nitro`。所有导入路径都已改变：

| 之前 | 之后 |
|---|---|
| `nitropack` | `nitro` |
| `nitropack/types` | `nitro/types` |
| `nitropack/runtime` | `nitro` |
| `h3`（用于服务端工具） | `nitro/h3` |

如果你在服务端代码中有显式导入，请更新它们：

```diff
- import { defineEventHandler, getQuery } from 'h3'
+ import { defineEventHandler, getQuery } from 'nitro/h3'
```

**对于模块作者**，类型扩展必须指向新的模块路径：

```diff
- declare module 'nitropack/types' {
+ declare module 'nitro/types' {
    interface NitroRuntimeConfig {
      myModule?: { /* ... */ }
    }
  }
```

路由规则的类型扩展又在另一个模块上。参阅[路由规则类型迁移到 `h3/rules`](#route-rule-types-move-to-h3rules)。

#### 服务端自动导入改为需显式启用（Server Auto-Imports Are Now Opt-In）

Nitro v3 移除了它自身的自动导入支持，因此 `defineEventHandler`、`getQuery`、`readBody` 和 `useRuntimeConfig` 等工具在服务端代码中不再是全局可用的。Nuxt 仍然提供它们，但在 Nuxt 5 中默认关闭。如果服务端代码使用了其中某个工具却没有导入它，构建会以 `NUXT_B9007` 警告，并列出需要添加的导入。

请在服务端代码中添加显式导入。优先使用 [`nuxt/server`](/docs/guide/going-further/server-imports)，自动导入解析到的正是它：

```diff [server/api/hello.ts]
+ import { defineEventHandler, getQuery } from 'nuxt/server'
+
  export default defineEventHandler((event) => {
    return getQuery(event)
  })
```

或者在迁移期间保留之前的行为：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    nitroAutoImports: true,
  },
})
```

这仅适用于 Nitro 和 h3 提供的那些工具。你自己在 `server/utils/` 和 `shared/utils/` 顶层文件中导出的内容仍然会被自动导入。

#### `server/utils/` 子目录中的文件不再被自动导入（Nested `server/utils/` Files Are No Longer Auto-Imported）

Nitro v2 会自动导入 `server/utils/` 下每个文件的导出，包括子目录中的文件。Nuxt 5 只扫描直接位于 `server/utils/` 中的文件，与它对 `app/utils/` 和 `shared/utils/` 的处理方式一致。如果服务端代码使用了某个嵌套文件的导出却没有导入它，构建会以 `NUXT_B9006` 警告。

请从直接位于 `server/utils/` 中的文件重新导出你需要的内容，或在使用处显式导入：

```ts [server/utils/index.ts]
export { requireAdminSession } from './admin/oauth'
```

若要在迁移期间继续扫描子目录，请启用 [`nitroLegacy.imports`](#your-own-server-directory)。

#### 服务端代码中 `#imports` 已被弃用，改用 `#imports/server`

服务端代码应从 `#imports/server` 导入：

```diff [server/api/hello.ts]
- import { defineEventHandler } from '#imports'
+ import { defineEventHandler } from '#imports/server'

  export default defineEventHandler(() => ({ hello: true }))
```

当你的服务端代码运行时 `#imports` 仍然可以被解析，因此尚未迁移的项目还能继续工作，但它不再带有类型信息：在你改用 `#imports/server` 之前，TypeScript 会报告它无法解析。

#### 错误处理：用 `status`/`statusText` 取代 `statusCode`/`statusMessage`

h3 v2 重命名了错误属性以与 Web 标准对齐：

```diff
  createError({
-   statusCode: 404,
-   statusMessage: 'Not Found',
+   status: 404,
+   statusText: 'Not Found',
  })
```

在服务端路由中，错误类现在是 `HTTPError`（取代从 `h3` 导入的 `createError`）：

```diff
- import { createError } from 'h3'
+ import { HTTPError } from 'nitro/h3'

  export default defineEventHandler(() => {
-   throw createError({ statusCode: 400, statusMessage: 'Bad request' })
+   throw new HTTPError({ status: 400, statusText: 'Bad request' })
  })
```

:::note
在你应用的 Vue 部分（即 `app/` 目录），Nuxt 的 `createError` 组合式函数继续可用，仍然是抛出错误的推荐方式。
:::

#### `createError` 不再返回 `HTTPError` 实例

`NuxtError` 现在是一个独立的类，而不再是 h3 `HTTPError` 的子类，因此 `instanceof HTTPError` 不再匹配用 Nuxt 的 `createError` 创建的错误。其他一切都没有变化：错误仍带有相同的属性，序列化方式相同，在 SSR 期间仍然会被映射到正确的 HTTP 响应。

如果你通过类来收窄错误类型，请改用下列断言函数之一：

```diff
- if (error instanceof HTTPError) {
+ if (HTTPError.isError(error)) {
    // 同时处理 `new HTTPError()` 和 Nuxt 的 `createError()`
  }
```

```diff
+ import { isNuxtError } from '#app'
+
+ if (isNuxtError(error)) {
+   // 收窄为用 Nuxt 的 `createError` 创建的错误
+ }
```

#### 服务端事件 API 变更（h3 v2）（Server Event API Changes）

`H3Event` 对象现在使用 Web 标准 API：

**请求属性：**
```diff
- event.path              // string
+ event.url.pathname      // URL 对象 - 使用 .pathname、.search、.hash

- event.method            // string
+ event.req.method        // 通过 Web Request 对象

- event.node.req.headers  // Node.js IncomingHttpHeaders
+ event.req.headers       // Web Headers API（.get()、.set()、.has()）
```

**响应属性：**
```diff
- event.node.res.statusCode = 200
+ event.res.status = 200

- event.node.res.statusMessage = 'OK'
+ event.res.statusText = 'OK'

- setResponseHeader(event, 'x-custom', 'value')
+ event.res.headers.set('x-custom', 'value')

- appendResponseHeader(event, 'set-cookie', cookie)
+ event.res.headers.append('set-cookie', cookie)
```

#### `useRuntimeConfig()` 不再接受 `event`

在 Nitro v3 中，`useRuntimeConfig()` 在服务端路由中不再需要（也不再接受）`event` 参数：

```diff
  export default defineEventHandler((event) => {
-   const config = useRuntimeConfig(event)
+   const config = useRuntimeConfig()
  })
```

runtime config 现在是一个由所有请求共享的单一对象，在服务端路由以及服务端渲染期间应用的 Vue 部分都是如此。在 Nuxt 4 中，每个请求都会拿到自己的副本，因此在渲染某个请求期间所做的修改（例如在插件中根据请求 host 设置 `runtimeConfig.public.siteUrl`）只在该请求内生效。在 Nuxt 5 中，它对所有后续请求都可见，并且对 `public` 和 `app` 键还会通过它们的 payload 对浏览器可见。请改为把按请求的值放在 `useState`、`nuxtApp.payload` 或 `event.context` 中。在开发模式下，如果渲染页面期间修改了 runtime config，Nuxt 会记录一条警告。

#### 路由规则：`statusCode` 重命名为 `status`

如果你定义了重定向路由规则，属性名已改变：

```diff
  export default defineNuxtConfig({
    routeRules: {
      '/old-page': {
-       redirect: { to: '/new-page', statusCode: 302 },
+       redirect: { to: '/new-page', status: 302 },
      },
    },
  })
```

目前 Nuxt 会把 `statusCode` 作为 `status` 应用并发出警告，因此尚未迁移的规则仍会保留它的状态码，而不会悄悄回退到默认值。这一回退将来会被移除。

#### 缓存路由规则忽略查询参数

被缓存的路由（`cache`、`swr`、`isr`）现在只以路径为键，查询字符串在处理函数运行之前就被丢弃。请设置 `allowQuery` 来保留它，可以设为 `true`，也可以设为参数名列表：

```ts
export default defineNuxtConfig({
  routeRules: {
    '/products': { cache: { swr: true, maxAge: 60, allowQuery: ['page'] } },
  },
})
```

同样的变化也适用于用 `defineCachedHandler`（在 `nitroLegacy` 下是 `defineCachedEventHandler`）包裹的处理函数，包括模块注册的这些处理函数：`getQuery(event)` 在它们内部会返回空对象。请在处理函数的选项中传入 `allowQuery`，或通过 `nitro.cache.defaults.allowQuery` 为所有缓存处理函数设置默认值：

```ts
export default defineCachedHandler(event => listModules(getQuery(event)), {
  maxAge: 60,
  allowQuery: ['category', 'version'],
})
```

缓存的处理函数与函数还会用不同的键存储它们的条目（自定义 `getKey` 的结果会被清理并追加一个哈希后缀），因此持久化缓存在升级后会从零开始，而任何按键读取缓存条目的代码都需要更新。如果某个缓存处理函数或函数解析耗时超过 30 秒，现在会以 `TimeoutError` 失败；对于预期较慢的情况，请设置 `maxResolveTime`（以秒为单位）。

#### 路由规则：`*` 匹配嵌套路径

路由规则模式现在遵循 [URLPattern](https://developer.mozilla.org/en-US/docs/Web/API/URL_Pattern_API) 语法。`*` 匹配任意数量的路径段而不再恰好匹配一个，因此键为 `/blog/*` 的规则同样适用于 `/blog/2026/hello`。要匹配单个路径段，请使用具名参数：

```diff
  export default defineNuxtConfig({
    routeRules: {
-     '/blog/*': { prerender: true },
+     '/blog/:slug': { prerender: true },
    },
  })
```

一个模式中只能包含一个 `*` 或 `**`，因此像 `/*/comments/**` 这样的键会导致构建失败。请只保留一个通配符，把其余的替换为具名参数，例如 `/:post/comments/**`。

:::read-more{to="https://github.com/h3js/rou3/blob/main/docs/migration.md" target="_blank"}
关于其他模式语法的变化，请参阅 rou3 迁移指南。
:::

#### 路由规则：正则约束不能匹配编码字符

路由规则模式中的正则约束（例如 `/products/:id([a-z0-9]+)`）是拿百分号编码后的路径来匹配的。如果某个约束可能匹配 `%`，或匹配路径中会被百分号编码的字符（例如 `[é]`、空格、`.`、`\S`，或像 `[^a-z]` 这样的取反字符类），或使用了单词边界（`\b` 或 `\B`），构建将失败。请改为列出约束允许的那些字符，或者使用不带约束的参数（例如 `/products/:id`）来匹配任意值。

#### 路由规则：`headers` 在处理函数之后应用

Nitro v3 会在处理函数运行之后才设置 `headers` 路由规则中的响应头，因此规则中的响应头会替换处理函数设置的同名响应头，包括处理函数返回的 `Response` 上的响应头。这一点在搭配 Nitro v3 的 Nuxt 4 上同样适用，并且 [Nitro v2 兼容层](#nitro-v2-compatibility)不会改变它。

#### 服务端存储（Storage）重命名为 KV

来自 `nitro/storage` 的 `useStorage()` 现在是来自 `nitro/kv` 的 `useKV()`，而 `nitro.storage` 选项现在是 `nitro.kv`。只在开发模式下生效的挂载点从 `nitro.devStorage` 迁移到 `$development` 下的 `nitro.kv`：

```diff
  export default defineNuxtConfig({
-   nitro: {
-     storage: { redis: { driver: 'redis' } },
-     devStorage: { redis: { driver: 'fs', base: './.data/redis' } },
-   },
+   nitro: {
+     kv: { redis: { driver: 'redis' } },
+   },
+   $development: {
+     nitro: {
+       kv: { redis: { driver: 'fs', base: './.data/redis' } },
+     },
+   },
  })
```

旧名称目前仍然可用，但会带有弃用警告。

#### 服务端文件名不能包含未知后缀

Nitro 会保留它在 `server/` 中扫描的文件名里带点的后缀，例如 `server/api/hello.get.ts` 中的 `.get`。像 `server/api/hello.world.ts` 这样的文件会导致构建失败（在开发模式下则会被跳过并报错），除非该后缀是一个已知的文件扩展名，例如 `server/routes/feed.json.ts` 中的 `.json`。请重命名文件，或把该后缀加入 `nitro.scanSuffixes`：

```ts
export default defineNuxtConfig({
  nitro: {
    scanSuffixes: ['world'],
  },
})
```

构建会以 `NUXT_B9014` 警告并列出需要添加的后缀。Nitro v2 会把这些后缀作为名称的一部分保留，因此在启用 [`nitroLegacy.config`](#your-own-server-directory) 时，Nuxt 会替你把它们加入 `nitro.scanSuffixes`，并以 `NUXT_B9013` 列出这些文件。

#### 路由规则类型迁移到 `h3/rules`

Nitro v3 基于 h3 构建路由规则，因此自定义路由规则要在此处声明，而不是在 `nitro/types` 上。`NitroRouteConfig` 和 `NitroRouteRules` 仍作为已弃用的别名导出，但它们现在是类型别名（type alias）而不是接口（interface），因此对它们进行扩展会以 `TS2300: Duplicate identifier` 失败。

需要声明的接口有两个，并且它们是有意分开的。`RouteRuleConfig` 是规则在 `nuxt.config` 中的样子，而 `RouteRules` 是匹配到的规则在运行时的样子：

```diff
- declare module 'nitropack/types' {
-   interface NitroRouteConfig {
+ declare module 'h3/rules' {
+   interface RouteRuleConfig {
      myModule?: { enabled: boolean }
    }
-   interface NitroRouteRules {
+   interface RouteRules {
      myModule?: { enabled: boolean }
    }
  }
```

任何没有被声明的规则，现在读回来的类型是 `unknown` 而不是 `any`，因此在使用处需要一次类型断言：

```diff
- const enabled = rules.myUndeclaredRule
+ const enabled = rules.myUndeclaredRule as boolean | undefined
```

#### 服务端 `tsconfig.json` 由 Nuxt 生成

现在由 Nuxt 自己生成 `.nuxt/tsconfig.server.json`，作为它按环境写入的多个 tsconfig 之一，而不再委托给服务端构建工具。如果你过去是通过 Nitro 来继承它的，请改用 Nuxt 的选项：

```diff
  export default defineNuxtConfig({
-   nitro: {
-     typescript: {
-       tsConfig: { compilerOptions: { /* ... */ } },
-     },
-   },
+   typescript: {
+     serverTsConfig: { compilerOptions: { /* ... */ } },
+   },
  })
```

`typescript.serverTsConfig` 在 Nuxt 4 中就已存在，并且会与 `nitro.typescript.tsConfig` 保持同步，因此如果你原本就在用它，这个改动对你没有任何影响。

#### 面向模块作者：其他变更（For Module Authors: Additional Changes）

- **Nitro 插件导入**：使用 `import { definePlugin } from 'nitro'`，这现在是默认要求。参阅[服务端自动导入改为需显式启用](#server-auto-imports-are-now-opt-in)。
- **路由规则辅助函数**：`basicAuth` 路由规则由中间件取代，新的 `cors` 规则取代手动的 CORS 接线。运行时细节请参阅 [Nitro 迁移指南](https://nitro.build/docs/migration)。
- **运行时钩子**：`nitroApp.hooks.hook('beforeResponse', ...)`、`nitroApp.hooks.hook('afterResponse', ...)` 和 `nitroApp.hooks.hook('render:response', ...)` 已被 `nitroApp.hooks.hook('response', ...)` 取代。`render:before` 钩子只在 [Nitro v2 兼容层](#nitro-v2-compatibility)处于激活状态时才会发出；要在页面渲染之前作出响应，请从服务端中间件里返回一个 `Response`。
- **来自 `nitro/app` 的 `getRouteRules()`**：在服务端，Nitro 辅助函数从 `getRouteRules(event)` 变为 `getRouteRules(method, pathname)`，它返回 `{ routeRules }`。

### 移除 `experimental.externalVue`（Removal of `experimental.externalVue`）

🚦 **影响级别**：最小

#### 发生了什么变化（What Changed）

`experimental.externalVue` 选项已被移除。当未启用 `vue.runtimeCompiler` 时，Vue 编译器依赖（`@babel/parser`、`@vue/compiler-core`、`@vue/compiler-dom`、`@vue/compiler-ssr`、`estree-walker`）如今在服务端构建产物中总是被替换为 mock 代理。

#### 变更原因（Reasons for Change）

随着向 Nitro v3 迁移，所有依赖默认都会被打包进服务端输出（不同于会把 `node_modules` 外部化的 Nitro v2）。`externalVue` 选项最初设计用于把 Vue 保留为外部依赖，这在避免打包进多份 Vue 时是必要的，但由于 Nitro v3 无论如何都会打包全部内容，该选项变成了空操作（no-op）。

Vue 的服务端构建包含完整的编译器工具链，会把 `@babel/parser`（465KB）及其他编译器包不必要地拉入服务端构建产物。这些编译器包只有在启用 `vue.runtimeCompiler` 进行运行时模板编译时才需要。

通过始终 mock 这些编译器依赖，默认的服务端构建产物体积减少了约 860KB（约 59%）。

#### 迁移步骤（Migration Steps）

如果你之前显式设置了 `experimental.externalVue`，现在应该移除它。

```diff
  export default defineNuxtConfig({
    experimental: {
-     externalVue: false,
    },
  })
```

:::note
如果你使用 `vue.runtimeCompiler: true`，真正的编译器包仍会像以前一样被包含。
:::

### 仅服务端的 Head 组合式函数不再被自动导入（Server-Only Head Composables Are No Longer Auto-Imported）

🚦 **影响级别**：最小

#### 发生了什么变化（What Changed）

`useServerHead`、`useServerHeadSafe` 和 `useServerSeoMeta` 已从 Nuxt 的自动导入中移除。它们仍从 `#app` 导出，因此显式导入依然有效。

`unhead.legacy` 选项在 Nuxt 5 上会被忽略：设置它会记录一条警告。Unhead 的遗留插件（`DeprecationsPlugin`、`PromisesPlugin`、`AliasSortingPlugin`）不再注册，Capo 排序始终开启。`TemplateParamsPlugin` 仍然会注册，因此 `%s`、`%siteName` 和 `%separator` 的标题插值不受影响。

这些组合式函数在客户端是空操作，并且在生产构建中 Nuxt 会把它们从客户端构建产物中 tree-shake 掉。

#### 迁移步骤（Migration Steps）

请改为在 `import.meta.server` 中调用 `useHead`，或者显式导入该组合式函数：

```diff
+ import { useServerHead } from '#app'
+
  useServerHead({ meta: [{ name: 'generator', content: 'Nuxt' }] })
```

从你的配置中移除 `unhead.legacy`：

```diff
  export default defineNuxtConfig({
-   unhead: {
-     legacy: true,
-   },
  })
```

### `experimental.parseErrorData` 不再可配置（`experimental.parseErrorData` Is No Longer Configurable）

🚦 **影响级别**：最小

#### 发生了什么变化（What Changed）

`experimental.parseErrorData` 选项已被弃用并强制开启。把它设为 `false` 会记录一条警告，其他情况下会被忽略，因此错误页上的 `error.data` 始终就是你传给 `createError` 的那个值。这里没有开关。

#### 变更原因（Reasons for Change）

Nuxt 渲染错误页时会在内部请求 `/__nuxt_error`，并随请求一起把错误传递过去。过去它会把错误摊开成每个字段一个查询参数，而查询参数值永远是字符串，所以 `error.data` 到达时是字符串，必须再解析回来。`parseErrorData` 当初就是为了选择退出这种解析。

现在错误是作为单个 JSON 编码的参数发送的，因此 `error.data` 保持它原本的结构，从来不会被字符串化。值也会保持类型，所以 `status` 是数字，布尔值是布尔值，而不是字符串 `'true'` 和 `'false'`。既然没有任何地方再把 `error.data` 字符串化，这个选项的存在就只是为了给仍期望字符串的应用把它再字符串化一遍。

#### 迁移步骤（Migration Steps）

移除该选项：

```diff
  export default defineNuxtConfig({
    experimental: {
-     parseErrorData: false,
    },
  })
```

如果你曾把它设为 `false` 以便自己解析 `error.data`，那么也请把那段解析去掉，因为 `error.data` 现在保持你传给 `createError` 的值：

```diff
  <script setup lang="ts">
  import type { NuxtError } from '#app'

  const props = defineProps({
    error: Object as () => NuxtError
  })

- const data = JSON.parse(props.error.data)
+ const data = props.error.data
  </script>
```

### 错误格式取决于错误抛出的位置（Error Format Depends on Where the Error Is Thrown）

🚦 **影响级别**：中等

#### 发生了什么变化（What Changed）

在渲染页面期间抛出的错误返回 HTML 错误页。在服务端路由或服务端中间件中抛出的错误返回 JSON。`Accept`、`Sec-Fetch-Mode` 和 `User-Agent` 请求头以及 `/api/` 路径前缀不再影响返回格式。

与 Nuxt 4 相比：

- **页面错误**会带上错误的状态码返回 HTML 错误页，即使请求接受 JSON 也是如此。这包括浏览器中的 `fetch()` 和 `$fetch()` 调用、`curl`，以及带 `Accept: application/json` 请求头的请求。
- **服务端路由和服务端中间件错误**返回 JSON，即使是浏览器导航请求。这包括针对页面路由抛错的服务端中间件，例如身份认证检查。
- **payload 错误**：针对 `_payload.json` 的请求仍然返回 JSON。

#### 变更原因（Reasons for Change）

在 Nuxt 4 中，请求头决定错误格式，因此同一个 URL 会对每一类客户端返回不同的错误响应。缓存就必须依据这些请求头来区分。对某个页面发起 `fetch()` 调用返回的是 JSON，而导航到同一个页面返回的是 HTML。现在每个 URL 都只有一种错误响应。

#### 迁移步骤（Migration Steps）

如果你在读取失败的页面请求的 JSON 响应体，例如 `$fetch('/some-page')` 返回的 `error.data`，请改为读取响应的状态码。若需要保留结构化的错误数据，请把它移入一个服务端路由。

如果你的服务端中间件会针对页面路由抛错以显示错误页，请把这个检查移到[路由中间件](/docs/directory-structure/app/middleware)中。路由中间件在页面渲染期间运行，因此它抛出的错误会返回错误页：

```ts [app/middleware/auth.global.ts]
export default defineNuxtRouteMiddleware((to) => {
  if (to.path.startsWith('/admin') && !useCookie('session').value) {
    throw createError({ status: 401, statusText: 'Unauthorized' })
  }
})
```

要恢复 Nuxt 4 的行为，请禁用 `experimental.inlineErrorRendering`。这同时也会恢复 Nuxt 4 渲染错误页的方式，即通过对 `/__nuxt_error` 的内部请求：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    inlineErrorRendering: false,
  },
})
```

### `giget` 现在变为可选（远程层）（`giget` Is Now Optional (Remote Layers)）

🚦 **影响级别**：最小

#### 发生了什么变化（What Changed）

`giget` 不再默认安装。它现在是 `@nuxt/kit` 的一个可选对等依赖，只有在需要下载 `extends` 中以远程 URL 指明的层时才用到：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: ['github:my-org/my-theme'],
})
```

本地层、`~~/layers/` 中的层，以及作为包安装的层都不受影响。

#### 变更原因（Reasons for Change）

大多数项目从不从远程源 extends，因此这个下载器会被安装到每个人的项目里，却只服务一小部分人。在解析配置时下载层，也是使用一个层最不具可复现性的方式：抓取发生在你的包管理器之外，因此不会进入 lockfile，而且除非你自己固定，它也没有固定到某个 revision。

#### 迁移步骤（Migration Steps）

**推荐做法：把层移入 `package.json`。** 所有主流包管理器都理解 git URL，因此远程层可以作为一个普通依赖。这样它会进入你的 lockfile、被固定到某个确切提交，并与其他依赖一起安装：

```json [package.json]
{
  "devDependencies": {
    "my-theme": "github:my-org/my-theme#4a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b"
  }
}
```

然后按包名 extends 它：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: ['my-theme'],
})
```

`#` 之后的部分可以是任何 commit-ish，因此标签（`#v1.2.0`）或 `#semver:^1.2.0` 也可以；只有完整的提交 SHA 才是真正不可变的。

**否则，请安装 `giget`**，并继续使用远程的 `extends` 条目：

:::code-group{sync="pm"}

```bash [npm]
npm install -D giget
```

```bash [yarn]
yarn add -D giget
```

```bash [pnpm]
pnpm add -D giget
```

```bash [bun]
bun add -D giget
```

:::

如果在没有安装 `giget` 的情况下解析了远程层，Nuxt 会报告是哪个 `extends` 条目需要它。

### `vue` 和 `vue-router` 成为对等依赖（`vue` and `vue-router` Are Peer Dependencies）

🚦 **影响级别**：最小

#### 发生了什么变化（What Changed）

`nuxt` 不再安装它自己那份 `vue` 和 `vue-router`。两者现在都是对等依赖，Nuxt 使用你项目所安装的那份来构建和运行你的应用。`vue-router` 是可选的，只有在启用 pages 时才需要（例如你的应用有 `pages/` 目录，或设置了 `pages: true`）。

:::code-group{sync="pm"}

### 构建时的代理支持改用 Node.js（Build-Time Proxy Support Uses Node.js）

🚦 **影响级别**：最小（如果你在代理后面构建，则为中等）

#### 发生了什么变化（What Changed）

当设置了 `HTTPS_PROXY` 或 `HTTP_PROXY`（或其小写形式）时，Nuxt 依赖 Node 内置的代理支持，把来自模块、预渲染以及你 `nuxt.config` 的构建时请求经由代理转发。`NO_PROXY` 中列出的主机则直接访问。

- **Node.js 24 与 26**：Nuxt 会调用 Node 的 [`http.setGlobalProxyFromEnv()`](https://nodejs.org/api/http.html#httpsetglobalproxyfromenvproxyenv)，因此使用 `node:http` 和 `node:https` 发起的请求与 `fetch` 一样都会走代理。当设置了 `HTTP_PROXY` 时 Node 会替换 `http.globalAgent`，当设置了 `HTTPS_PROXY` 时会替换 `https.globalAgent`，所以在 `loadNuxt` 运行之前赋值的全局 agent（例如在以编程方式运行 Nuxt 的脚本中设置的）会被替换掉。模块在 setup 期间分配的 agent 会被保留。
- **Node.js 22**：Nuxt 不再依赖 `undici`，因此不像 Nuxt 4 那样安装 `EnvHttpProxyAgent`。除非开启 Node 自身的代理支持，构建时的请求会直接发往目标，并且在设置了代理变量时 Nuxt 会记录一条警告。

当设置了 `NODE_USE_ENV_PROXY=0` 时、当 Node 自身的代理支持已经开启（`NODE_USE_ENV_PROXY=1` 或 `--use-env-proxy`）时，或者当安装了除 undici 默认 `Agent` 之外的全局 dispatcher（例如 `ProxyAgent`）时，Nuxt 不会改动代理配置。在 Node.js 24 与 26 上，如果全局 dispatcher 本身就是一个 undici `Agent`（例如用自定义 TLS 选项创建的），它无法与默认的那个区分开，因而会被替换。

#### 迁移步骤（Migration Steps）

如果你在 Node.js 22 上于代理之后构建，请在代理变量旁同时设置 `NODE_USE_ENV_PROXY=1`，这会让 `fetch`、`node:http` 和 `node:https` 都经由代理转发；或者升级到 Node.js 24：

```bash [Terminal]
NODE_USE_ENV_PROXY=1 HTTPS_PROXY=http://proxy.example.com:8080 npx nuxt build
```

如果你在 Node.js 24 或 26 上于代理之后构建，而某个模块用 `node:http` 或 `node:https` 访问内部主机，请把这些主机加入 `NO_PROXY`：

```bash [Terminal]
HTTPS_PROXY=http://proxy.example.com:8080 NO_PROXY=internal.example.com npx nuxt build
```

取决于 Node.js 版本，`fetch` 与 `node:http` 会以不同形式匹配 `NO_PROXY` 中的 IPv6 地址，因此请同时列出裸写形式和带方括号的形式：

```bash [Terminal]
HTTPS_PROXY=http://proxy.example.com:8080 NO_PROXY=localhost,::1,[::1] npx nuxt build
```

要保留自定义的全局 agent 或 undici `Agent` dispatcher，或者完全选择退出代理支持（这同时也会消除 Node.js 22 上的警告），请设置 `NODE_USE_ENV_PROXY=0`。

### 移除遗留的 `_renderResponse` 支持（Removal of Legacy `_renderResponse` Support）

🚦 **影响级别**：最小

#### 发生了什么变化（What Changed）

不再把 `ssrContext._renderResponse` 作为回退来检查。只有内部的 `ssrContext['~renderResponse']`（由 Nuxt 自己的路由组合式函数设置）会被使用。

#### 变更原因（Reasons for Change）

在 [#33896](https://github.com/nuxt/nuxt/pull/33896) 把内部 API 迁移到 `~renderResponse` 之后，`ssrContext` 上的 `_renderResponse` 属性作为向后兼容的回退被保留了下来。代码中的 TODO 注释表明它应在 Nuxt v5 中移除。

#### 迁移步骤（Migration Steps）

如果你直接设置过 `ssrContext._renderResponse`（它从来不是公开 API），请改用 `ssrContext['~renderResponse']`。Nuxt 的路由组合式函数已经在使用新属性，因此如果你是经由 `navigateTo` 或路由中间件，则无需更改。

### 非 async 的 `callHook`（Non-Async `callHook`）

🚦 **影响级别**：最小

#### 发生了什么变化（What Changed）

随着升级到 [hookable v6](https://github.com/unjs/hookable)，`callHook` 现在可以返回 `void`，而不再总是返回 `Promise<void>`。这是一项显著的性能改进，它在没有注册任何钩子或所有钩子都是同步的情况下避免了不必要的 `Promise` 分配。

Nuxt 4 会用 `Promise.resolve()` 包裹 `callHook`，以便现有的 `.then()` 和 `.catch()` 链式调用继续工作。该包裹已被移除，并且 `experimental.asyncCallHook` 现在默认为 `false`。

:::tip
这会影响构建时的 Nuxt 钩子（由 Nuxt 模块使用）和运行时的 Nuxt 钩子（你可能会在应用代码中使用）。
:::

#### 变更原因（Reasons for Change）

Hookable v6 的 `callHook` 快了 20-40 倍，因为它在不需要时不会创建 `Promise`。这对钩子调用点很多的应用有益。

#### 迁移步骤（Migration Steps）

如果你或你的模块在使用 `callHook` 时接了 `.then()` 或 `.catch()` 链式调用，请改用 `await`：

```diff
- nuxtApp.callHook('my:hook', data).then(() => { ... })
+ await nuxtApp.callHook('my:hook', data)
```

```diff
- nuxtApp.hooks.callHook('my:hook', data).catch(err => { ... })
+ try { await nuxtApp.hooks.callHook('my:hook', data) } catch (err) { ... }
```

要让 `callHook` 始终返回一个 `Promise`：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    asyncCallHook: true,
  },
})
```

### 仅客户端组件的注释占位符（Client-Only Comment Placeholders）

🚦 **影响级别**：最小

#### 发生了什么变化（What Changed）

仅客户端组件（`.client.vue` 文件和 `createClientOnly()` 包装器）如今在服务端渲染的是一个 HTML 注释（`<!--placeholder-->`），而不再是一个空的 `<div>` 元素。

#### 变更原因（Reasons for Change）

当占位 `<div>` 与实际组件根使用相同的标签名时，Vue 运行时在水合期间会跳过重新调用 `setScopeId`，导致组件挂载后缺失 scoped 样式。使用注释节点可以完全避免标签名冲突。

#### 迁移步骤（Migration Steps）

如果你依赖占位 `<div>` 来继承属性（`class`、`style` 等）以满足布局目的（例如预留空间以防止布局偏移），请改为把组件包在带 `#fallback` 插槽的 `<ClientOnly>` 中：

```diff
- <MyComponent class="placeholder" style="min-height: 200px" />
+ <ClientOnly>
+   <MyComponent />
+   <template #fallback>
+     <div class="placeholder" style="min-height: 200px"></div>
+   </template>
+ </ClientOnly>
```

要恢复之前的 `<div>` 占位行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    clientNodePlaceholder: false,
  },
})
```

### 更严格的副作用导入（Stricter Side-Effect Imports）

🚦 **影响级别**：最小

#### 发生了什么变化（What Changed）

Nuxt 生成的 `tsconfig.json` 启用了 [`noUncheckedSideEffectImports`](https://www.typescriptlang.org/tsconfig/#noUncheckedSideEffectImports)。这是 TypeScript 7 中的默认值，因此提前采用可以让你的项目在那次升级之前就保持一致。

开启该选项后，TypeScript 无法解析为模块的纯副作用导入（`import './setup'`）现在会成为类型错误，而以前会被忽略。这只影响类型检查（`nuxt typecheck` 和你的编辑器），不影响运行时行为。

#### 变更原因（Reasons for Change）

无法解析的副作用导入以前被静默忽略，因此拼写错误或已删除的文件都能通过类型检查。把它们标出来可以发现这些错误，并与 TypeScript 7 的默认值保持一致。

#### 迁移步骤（Migration Steps）

如果类型检查现在因为对非代码资源的副作用导入（例如 `import '~/assets/styles.css'`）而报错，请添加一个环境模块声明，让 TypeScript 知道该导入是有效的：

```ts [types.d.ts]
declare module '*.css' {}
```

:::tip
你可以通过在你的 `nuxt.config` 中禁用该选项来恢复之前的行为：

<!-- @case-police-ignore tsConfig -->

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  typescript: {
    tsConfig: {
      compilerOptions: {
        noUncheckedSideEffectImports: false,
      },
    },
  },
})
```
:::

### Vue Options API 默认禁用（Vue Options API Disabled by Default）

🚦 **影响级别**：最小

#### 发生了什么变化（What Changed）

Nuxt 把 Vue 的 [`__VUE_OPTIONS_API__`](https://vuejs.org/api/compile-time-flags#VUE_OPTIONS_API) 特性标志设为 `false`，这会把 Vue 的 Options API 运行时从客户端构建产物中编译移除。

#### 变更原因（Reasons for Change）

尽管大多数 Nuxt 应用都是用 Composition API 和 `<script setup>` 编写的，Options API 运行时仍会随每个客户端构建产物一起发布。移除它可以缩小客户端构建产物（在一个最小应用上约为 minified 6 kB / gzipped 2 kB）。

#### 迁移步骤（Migration Steps）

如果你的任何组件（或某个依赖的组件）使用了 Options API（`export default { data() {}, methods: {}, ... }`），请在你的 `nuxt.config` 中重新启用它：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  vue: {
    optionsApi: true,
  },
})
```

:::note
`defineNuxtComponent` 不受影响：它的 `asyncData` 和 `head` 选项是通过 `setup()` 而非 Vue Options API 处理的，因此无论此标志如何，它都能工作。
:::

### 类型化页面默认启用（Typed Pages Enabled by Default）

🚦 **影响级别**：最小

#### 发生了什么变化（What Changed）

`experimental.typedPages` 现在默认启用。Nuxt 会根据你的 `pages/` 目录生成带类型的路由名称与路径，因此 `useRoute`、`navigateTo`、`<NuxtLink>` 和 `router.push` 这类用法会针对你真实存在的路由进行类型检查。

#### 变更原因（Reasons for Change）

类型化路由能在类型检查阶段而不是运行阶段发现失效的链接和过期的路由名，而且它现在是 `vue-router` 的原生能力，因此是一个合理的默认值。

#### 迁移步骤（Migration Steps）

如果你引用了并不存在的路由（例如 `to` prop 中的拼写错误，或在 `pages/` 目录之外动态定义的路由），类型检查现在会报错。请修正该引用，或为你在运行时添加的路由扩展生成的路由类型。

要选择退出并恢复之前的行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    typedPages: false,
  },
})
```

### 类型化 `$fetch` 基于生成的路由类型重建（Typed `$fetch` Rebuilt on Generated Route Types）

🚦 **影响级别**：中等

#### 发生了什么变化（What Changed）

`$fetch` 和 `useFetch` 的类型来自 Nuxt 的服务端构建工具所报告的路由，而不再来自 nitro 的 `InternalApi` 接口。除了响应类型之外，匹配的处理函数所校验的 `body`、`query` 或 `headers` 现在也会在该调用上强制约束，而路由没有处理的方法则会被拒绝。

由此带来两点：

- 你过去在 nitro 的 `InternalApi` 上手动扩展的路由不再被识别。请改为扩展来自 `@nuxt/schema` 的 `ServerRoutes`。
- `$fetch` 和 `useFetch` 不再接受 `params` 选项。它原本只是 `query` 的别名。

用 `defineCachedHandler` 编写的路由，或用 `defineCachedEventHandler` 或 `cachedEventHandler` 编写的路由，其类型由被缓存的那个处理函数的返回值决定。如果直接调用，缓存处理函数解析为它所服务的 `Response`。

对于生成的路由类型没有描述的路径，仍然可以解析，类型为 `unknown`，除非你启用了 [`experimental.strictRouteTypes`](/docs/guide/going-further/experimental-features#strictroutetypes)。

#### 变更原因（Reasons for Change）

Nitro v3 移除了 typed fetch，而旧实现大约在 300 个路由之后就难以为继。新的生成路由类型无论路由数量多少，检查开销都相同，并且携带了足以同时为请求和响应提供类型的信息。移除 `params` 是为了把这个名字腾出来，留给将来的具名路由参数使用。

#### 迁移步骤（Migration Steps）

把任何 `params` 选项移到 `query`：

```diff
  const { data } = await useFetch('/api/search', {
-   params: { q: 'nuxt' },
+   query: { q: 'nuxt' },
  })
```

把任何手动添加的路由类型扩展从 `InternalApi` 移到 `ServerRoutes`：

```diff [shared/server-routes.d.ts]
- declare module 'nitropack' {
-   interface InternalApi {
-     '/api/hello': { get: { message: string } }
-   }
- }
+ import type { Endpoint } from 'nuxt/app'
+
+ declare module '@nuxt/schema' {
+   interface ServerRoutes {
+     '/api/hello': {
+       [Endpoint]: {
+         GET: { response: { message: string } }
+       }
+     }
+   }
+ }
```

替换那些被标注为 `Parameters<typeof $fetch>[1]` 的选项。在使用 nitropack 时，该类型是 nitropack 的 `NitroFetchOptions`，它接受任何方法以及 ofetch 自身的选项类型。而在 Nitro v3 下，`$fetch` 的类型来自你应用的路由，从它的签名上读出来的类型并不是它接受用于 `string` URL 的类型：取决于你的路由，它会解析为 `never`，或解析为在以 `string` URL 调用时会被拒绝的选项。

对于你的应用并不提供的 URL（此时你会指明响应类型），请把选项类型写成来自 `nuxt/app`（在应用代码中也可以来自 `#app`）的 `FetchOptions`。这是 Nuxt 的类型：同名的 ofetch 类型把 `method` 标注为普通 `string`，而类型化的 `$fetch` 不接受它，因此已经导入了 ofetch 的 `FetchOptions` 的文件需要给其中一个起别名。调用 ofetch 自带 `$fetch` 的服务端代码继续使用 ofetch 自己的选项类型：Nuxt 的 `FetchOptions` 是针对 Nuxt 的类型化 `$fetch` 的。

```diff [app/utils/fetch-registry.ts]
+ import type { FetchOptions } from 'nuxt/app'
+
- export function fetchRegistry<T> (url: string, options: Parameters<typeof $fetch>[1] = {}) {
+ export function fetchRegistry<T> (url: string, options: FetchOptions = {}) {
    return $fetch<T>(url, options)
  }
```

对于包裹你自己路由、且默认值不同的封装，请使用 `$fetch.create`，它会保留路由类型：

```diff [app/utils/api.ts]
- export function api<T> (url: string, options: Parameters<typeof $fetch>[1] = {}) {
-   return $fetch<T>(url, { ...options, headers: { 'x-client': 'app' } })
- }
+ export const api = $fetch.create({ headers: { 'x-client': 'app' } })
```

:::read-more{to="/docs/getting-started/data-fetching#typed-routes"}
阅读更多关于类型化路由的内容。
:::

### `$fetch` 在浏览器中不再是全局变量（`$fetch` Is No Longer a Global in the Browser）

🚦 **影响级别**：最小

#### 发生了什么变化（What Changed）

客户端构建不再设置 `globalThis.$fetch`。调用 `$fetch` 的代码现在以导入的方式从 `#build/fetch` 获得它，包括那些不使用自动导入的代码，例如模块的运行时文件。在服务端，`globalThis.$fetch` 仍然会被设置。

#### 变更原因（Reasons for Change）

从不调用 `$fetch` 的应用不再把 `ofetch` 发送到浏览器。

#### 迁移步骤（Migration Steps）

如果你在浏览器中读取或替换 `globalThis.$fetch`，请改用一个提供你自己实例的插件：

```diff [app/plugins/api.ts]
  export default defineNuxtPlugin(() => {
-   globalThis.$fetch = $fetch.create({ baseURL: '/api' })
+   return {
+     provide: {
+       api: $fetch.create({ baseURL: '/api' }),
+     },
+   }
  })
```

随后在你原本使用被替换的全局变量的地方改为调用 `useNuxtApp().$api`。

### TypeScript `baseUrl` 被忽略（TypeScript `baseUrl` Is Ignored）

🚦 **影响级别**：最小

#### 发生了什么变化（What Changed）

Nuxt 会从它生成的 TypeScript 配置中移除 `compilerOptions.baseUrl`。相对的 Nuxt 和 Nitro 别名现在从 Nuxt 的构建目录解析，而不是从自定义的 `baseUrl` 解析。

#### 变更原因（Reasons for Change）

TypeScript 6 已弃用 `baseUrl`，并且在使用 `paths` 时它也不再是必需的。移除该选项同时可以让 Nuxt 生成的别名一致地锚定在包含它们的那份生成配置上。

#### 迁移步骤（Migration Steps）

从你的 Nuxt TypeScript 配置中移除 `baseUrl`。如果你曾用它来锚定一个相对的 Nuxt 或 Nitro 别名，请改为把该别名写成绝对路径：

```diff [nuxt.config.ts]
+ import { fileURLToPath } from 'node:url'
+
  export default defineNuxtConfig({
    alias: {
-     images: './assets/images',
+     images: fileURLToPath(new URL('./assets/images', import.meta.url)),
    },
-   typescript: {
-     tsConfig: {
-       compilerOptions: {
-         baseUrl: '..',
-       },
-     },
-   },
  })
```

## Nitro v2 兼容性（Nitro v2 Compatibility）

上面列出的 Nitro v3 变更涉及大量服务端代码。但你无需把它们全部处理完，Nuxt 5 也能构建。Nuxt 5 自带一个兼容层，可以按原样运行较旧的服务端代码，因此你可以先升级，之后再逐步迁移。

### 模块的服务端代码（Module Server Code）

模块会被自动覆盖。如果某个模块的服务端文件从 `h3`、`nitropack`、`#internal/nitro` 或 `#imports` 导入，Nuxt 会为其代码提供它所期望的东西：h3 v1 的辅助函数、映射到 Nitro v3 的旧 `nitropack` 路径、`useRuntimeConfig(event)`，以及 v1 的事件属性。

构建会告诉你哪些模块被这样处理了：

```text
WARN [NUXT_B9003] Nitro v2 compatibility was applied to server code from 1 module, because of what it imports:
  - some-module (imports `h3`, `nitropack/runtime`)
```

这条提示不需要你做任何处理。它是说给该模块的作者听的，同时也意味着该模块的后续版本将不再需要这个兼容层。

:::read-more{to="/docs/guide/modules/server-compatibility"}
如果这个模块是你自己写的，了解如何编写能在任一 Nitro 版本上运行的服务端代码。
:::

### 你自己的 `server/` 目录（Your Own `server/` Directory）

你自己的服务端代码默认不在覆盖范围内，因为你得到的那些错误正是告诉你工作在哪里。当 `nitroLegacy` 关闭时，`NUXT_B9005` 会列出你 `server/` 目录中那些从 `nitropack` 导入、使用了 h3 v2 不再导出的 h3 v1 辅助函数、或读取 `event.node` 的文件。如果你的项目自身依赖 h3 v1，那么你服务端代码中的 `h3` 导入会解析到它，而不是解析到 h3 v2，并且在你移除该依赖或开启 `nitroLegacy.h3` 之前，`NUXT_B9009` 会列出从 `h3` 导入的文件。如果你想先完成升级再处理这些工作，请开启 `nitroLegacy`：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  nitroLegacy: true,
})
```

开启之后，`import { defineEventHandler, getQuery } from 'h3'`、`useRuntimeConfig(event)`、`defineNitroPlugin`、`cachedEventHandler`、`useEvent`、来自 `server/utils/` 子目录的自动导入、不带 `route` 注册的处理函数，以及名称中带点后缀的服务端文件（例如 `server/middleware/auth.global.ts`），都将照常工作。返回字符串的处理函数在没有设置 content type 时仍然以 `text/html` 发送；返回 `null` 的处理函数仍然响应 `204 No Content`，或者响应它所设置的状态码。

那些由 h3 v1 辅助函数结束响应的写法仍然会结束响应。当用 `defineEventHandler` 定义的处理函数调用 `sendRedirect`、`sendNoContent`、`send`、`sendStream`、`sendError`、`sendProxy` 或 `sendWebResponse`，或用 `handleCors` 处理了预检请求时，即使该处理函数没有返回任何内容，Nuxt 也会把那个响应发送出去，请求不再继续。用 `defineEventHandler({ handler, websocket })` 定义的处理函数在收到 WebSocket 升级请求时仍然会走到它的 `websocket` 钩子。

开启 `nitroLegacy.h3` 后，Nuxt 还会移除任何把 `h3` 指向 h3 v1 的服务端别名（例如某个模块为了让 `h3` 解析到 `nitropack` 所依赖的那份而设置的别名），并以 `NUXT_B9015` 报告它。Nitro v3 无法运行 h3 v1，因此在别名被移除后，Nitro v2 的代码得到 h3 v1 的辅助函数，而其他服务端代码得到 h3 v2。

每一部分都是一个独立的开关，因此你可以一次迁移一项：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  nitroLegacy: {
    h3: true, // `h3` 解析到 h3 v1 的辅助函数
    specifiers: true, // `nitropack`、`nitropack/runtime`、`#internal/nitro`
    runtimeConfig: true, // `useRuntimeConfig(event)` 的签名
    imports: false, // Nitro v2 的自动导入名称，以及嵌套的 `server/utils/` 文件
    config: false, // Nitro v2 的配置结构与带点后缀的服务端文件名
  },
})
```

`beforeResponse`、`afterResponse`、`render:before` 和 `render:response` 钩子不需要开关。只要该兼容层处于激活状态（无论是为你的代码还是为某个模块的代码），Nuxt 就会从 Nitro v3 的 `response` 钩子发出 `beforeResponse` 和 `afterResponse`，并在每次页面渲染前后发出 `render:before` 和 `render:response`。它会报告任何无法处理的情况。该兼容层所覆盖的 Nitro v2 插件，以及从 `nitropack/runtime` 导入的 `useNitroApp()`，同样会得到一个始终返回 promise 的 `nitroApp.hooks.callHook()`，与 Nitro v2 一致，因此 `callHook('my-hook').catch(...)` 仍能工作。

在搭配 Nitro v3 的 Nuxt 4 上，当 `nitroLegacy.config` 开启时，错误响应会带上 `x-content-type-options: nosniff`、`x-frame-options: DENY` 和 `referrer-policy: no-referrer` 响应头，并且 JSON 错误响应还会带上 `content-security-policy: script-src 'none'; frame-ancestors 'none';`。在 Nuxt 5 上，以及在关闭 `nitroLegacy.config` 的 Nuxt 4 上，Nuxt 不会向错误响应添加这些响应头。

在 `nitroLegacy.config` 开启时，`prerender:done` 这类构建钩子可以读写 Nitro v2 的构建时存储 `nitro.storage`。它带有 `root:`、`src:`、`build:`（你的 `buildDir`）、`cache:` 和 `data:` 挂载点，以及你在 `nitro.kv` 和 `nitro.devStorage` 中声明的那些挂载点。开发服务器和预渲染器会拿到相同的 `build:`、`cache:` 和 `data:` 挂载点，因此预渲染器写入 `build:` 的内容可以在预渲染完成后从 `nitro.storage` 读取。你的生产服务器不会拿到它们。与 Nitro v2 不同的是，在开发模式和预渲染期间，缓存的处理函数与函数仍会使用内存缓存驱动，除非你设置了 `nitro.cache.driver` 或自己声明一个 `cache` 挂载点。

### 兼容层不覆盖的部分（What the Layer Doesn't Cover）

- **未声明的依赖。** `nitropack` v2 会把它自己的依赖放进服务端构建产物，因此某个文件可以在没有依赖它的前提下导入像 `lru-cache` 这样的东西并正常工作。请把该包加入你自己的依赖，或者反馈给需要它的模块。
- **类型。** 该兼容层主要改变你的服务端代码如何运行，而不是它如何通过类型检查。开启 `nitroLegacy.specifiers` 后，在你的代码或某个模块的代码中对 `nitropack` 或 `nitropack/types` 的类型扩展，会作用于同名的 Nitro v3 接口，例如 `NitroRuntimeHooks`。对 `nitropack/runtime` 和 `#internal/nitro` 的类型扩展不会被识别，而路由规则要在别处声明（参阅[路由规则类型迁移到 `h3/rules`](#route-rule-types-move-to-h3rules)）。开启 `nitroLegacy.h3` 后，在服务端 tsconfig 中 `h3` 解析到 Nitro 的 h3 v2，即使你的项目依赖的是 h3 v1，这样从 `h3` 导入的 `H3Event` 就与你的处理函数实际收到的事件一致。在该类型上，`event.node` 是可选的。只有 h3 v1 才有的辅助函数，例如 `send`、`sendError` 或 `isStream`，从 `h3` 导入时仍然可用，但无法以这种方式通过类型检查。它们的自动导入是带类型的。服务端路由中的 `useRuntimeConfig(event)` 仍然会被报告出来，因为类型化的 `$fetch` 响应检查会在应用代码之外一并检查路由文件。出于同样的原因，服务端路由里来自 `h3` 的 `H3Event` 仍然会被应用的 tsconfig 报告出来，而它把 `h3` 解析到你项目的依赖。
- **事件对象。** 使用默认构建工具时，`event` 是 h3 v2 的事件。该兼容层会补回 h3 v2 去掉的一些东西，例如 `event.context.nitro`、`event.context._nitro.routeRules`，以及在没有 Node 形态对象的运行时上提供一个 Node 形态的 `event.node`。在进程内发起的请求，例如服务端对某个自有路由或某个正在预渲染的页面发起的 `$fetch` 或 `useFetch`，也会得到一个，其中 `event.node.req.socket` 的 `readyState` 为 `'readOnly'`，与 Nitro v2 一致。它的 `remoteAddress` 是发起该调用的请求的客户端地址，如果没有则为 `undefined`。你在 `event.node.res` 上设置的响应头和状态会应用于 Nitro 实际发送的响应。
- **预渲染期间的 `close` 钩子。** Nitro v3 停止预渲染器时不会调用运行时的 `close` 钩子，因此在其中保存数据的监听器永远不会运行，数据也就丢失了。对于注册了这类监听器的每个 Nitro v2 插件，Nuxt 会以 `NUXT_E8017` 点名它。请改为在预渲染每个路由时就保存数据，并在某个构建钩子中读回。

### 迁移步骤（Migration Steps）

1. 升级、构建，并阅读这些提示。`NUXT_B9003` 说的是模块，因此那是它们的作者的工作而不是你的。你自己 `server/` 目录中的错误才是你需要处理的。
2. 把你的服务端导入迁移到 [`nuxt/server`](#server-imports-move-to-nuxtserver)（从 Nuxt 4.6 起可用），并把其中未覆盖的内容迁移到 `nitro/h3` 或 `nitro/*`。在这期间保持 `nitroLegacy` 关闭。
3. 只有在需要抢先发布而尚未完成迁移时才开启 `nitroLegacy`。然后一次把其中一个开关设为 `false` 并修好随之而来的问题，直到你可以完全移除该选项。
4. 如果 `NUXT_B9003` 仍然点到某个模块，请检查是否有更新的版本，没有的话就去提一个 issue。
